## Расход подписки и условная автоматизация

**2026-09-08, подтверждённые требования пользователя:** немедленно отключить все хуки на время подготовки спеки по расходу лимитов. Возвращать хуки и LSP только при доказанной пользе для результативности, качества и времени до проверенного результата; полный отказ от LSP допустим. Это решение заменяет прежнее требование безусловной автоматической диагностики всех выбранных языков.

Если автоматический LSP будет сохранён, он запускается **только после фактического создания или изменения содержимого поддерживаемых файлов и только для этих файлов**. Чтение, неизменившиеся команды, удаление без создания/изменения, старт/завершение работы и накопленные проверки не являются поводом для запуска или повторной выдачи.

**Последующее уточнение:** все автоматизированные интерфейсы и точки ввода должны передавать необходимый минимум информации. Без новых значимых данных — молчание; при результате или проблеме — сведения для следующего решения, подробности по запросу. Требование распространяется также на MCP, служебные уведомления, обёртки и передачу результатов агентов. Компактность не должна скрывать существенные ошибки или неопределённость проверки.

**Последующее поручение пользователя:** полностью реализовать [reduce-subscription-waste](../openspec/changes/archive/2026-09-08-reduce-subscription-waste/proposal.md) и архивировать после успешной реализации. Итоговая выбранная конфигурация и проверки собраны в [отчёте реализации](evidence/subscription-efficiency.md): обычные диагностические и Stop-хуки выключены; последующее RTK-исключение описано ниже. Отдельный `harness-lsp` выведен из управляемой установки, четыре MCP сохранены. Для явных операций Serena проверен Python; остальные языковые кандидаты не являются обязательной установкой. Это выбор реализации по принятому правилу пользы, не новое требование пользователя к конкретному backend. Astra `xhigh` и предпочтительный Grok middle сохраняются; процент экономии недельной квоты не установлен.

**Подтверждённое архитектурное направление:** упрощать вокруг готовых возможностей Serena, если они закрывают принятые потребности. Приоритет — её навигация, подходящие правки и диагностика вместе со штатными проверками проекта; отдельные серверы и доработки оправданы только доказанным важным пробелом. Неподходящую автоматическую диагностику оставлять выключенной, а не создавать обходную инфраструктуру ради неё. Обсуждаются проверки законченной группы изменений, в том числе в ответе edit-инструмента без native hooks; обязательная доля 99% не установлена, генераторы и восстановление сохраняют подходящий запасной путь. [Дизайн](../openspec/changes/archive/2026-09-08-reduce-subscription-waste/design.md#8-serena-as-the-shared-diagnostic-provider-requested-alternative) фиксирует наблюдения и проверку варианта; автоматизация этим решением не включается.

**Подтверждено пользователем после обсуждения полезности хуков:** работа без хуков — постоянный режим по умолчанию, включая завершение спеки. Не возвращать рутинную загрузку инструкций, широкую повторную диагностику и дополнительные проверки/продолжения через Stop. Редкое исключение требует конкретной потребности, отсутствия достаточного штатного механизма и доказанной пользы; оно должно быть узким, детерминированным, ограниченным по времени и молчаливым при успехе. Примеры защиты перед операцией, уборки ресурсов своей сессии и локального уведомления не являются поручением их реализовать; на момент этого решения исключений не было; последующее RTK-исключение записано ниже. Отсутствие вывода само по себе не оправдывает задержки и стоимость сопровождения.

## Экономия токенов в рабочем процессе

**2026-09-08, подтверждённый выбор пользователя:** RTK (в сообщении `rkt`), Code Mode, развитие использования Serena/Codebase Memory MCP, `apply_patch`, меньше повторных действий и adaptive reasoning под задачу. Экономия входящих и исходящих токенов должна сохранять качество и скорость либо снижать их крайне незначительно; 60–90% для поддерживаемых команд достаточно, чтобы рассматривать RTK. Это ориентир из исследования, не измерение всей сессии или квоты.

**Явное исключение к режиму без хуков:** пользователь разрешил быстрые хуки для RTK. Это не возвращает обычные диагностические, контекстные или Stop-хуки и заменяет прежнюю запись об отсутствии принятых исключений только в этой части. Пользователь поручил создать спеку, сразу реализовать её полностью и затем архивировать. [optimize-agent-token-workflow](../openspec/changes/archive/2026-09-08-optimize-agent-token-workflow/proposal.md) реализован, глобально подключён и архивирован 2026-09-08; девять задач закрыты на основании [проверок](evidence/token-workflow.md). Измеренные сокращения вывода не означают такой же экономии всей подписки.

**Уточнение после первых измерений:** дополнительные 30–60 мс пользователь считает несущественными по сравнению с пользой от экономии токенов. Это оценка приемлемости такой задержки; сохранение корректности и проверка полного пути остаются обязательными.

**Уточнение после native-проверки:** пользователь также явно принял дополнительные 250–313 мс штатного запуска хука Codex: «Вообще не проблема». Предварительный более строгий порог дизайна не блокирует поставку по этой измеренной задержке. Полные измерения, включая первый вызов, остаются в отчёте; это не разрешение снижать корректность или скрывать существенное дальнейшее замедление.

## Назначение

`codex-harness` — переносимая основа глобальной настройки и расширения Codex CLI для разработки в других репозиториях. Польза набора оценивается по работе в целевых проектах.

Источник подходов для адаптации — `opencode-kit`. Из него переносим возможности, которые помогают достигать принятого результата быстрее и с нужным качеством.

## Результативность, качество и скорость

**2026-09-08, подтверждённое указание пользователя:** постоянно оценивать, насколько удобно разрабатывать код и в целом работать в текущем репозитории. Сначала обеспечить удобную и рабочую среду, затем реализовывать зависимые изменения. Проверять фактическую поддержку языков, охват исходников, навигацию, редактирование, запуск и проверки; самостоятельно устранять конкретные неудобства в рамках задачи, в том числе обнаруженные по ходу работы и требующие повторных ручных обходов. Канонический порядок — [подготовка рабочей среды](../global/principles-of-work.md#working-environment-before-implementation), локальное применение — [AGENTS.md](../AGENTS.md). Подготовка остаётся соразмерной задаче и переиспользуется, пока среда не изменилась.

**2026-09-08, подтверждённое указание пользователя:** добавить Rust в Serena для `codex-harness` и обеспечить анализ `tools/` перед перезапуском сессии. Это явный выбор дополнительного языка для работы над Rust-миграцией; обычные диагностические и Stop-хуки остаются выключенными. Реестр переиспользует установленный rust-analyzer, язык включается в конфигурации этого проекта; остальные проекты не перенастраиваются.

Все три свойства обязательны для оценки пользы набора:

- **Результативность:** довести согласованную задачу до завершения и получить требуемый результат. Скорость и качество имеют смысл при достигнутом результате.
- **Качество:** ориентироваться на отсутствие P0/P1 инцидентов и багов в получившихся фичах. Выявленные P0/P1 устранять до завершения работы; выбирать проверки по реальным сценариям и существенным рискам.
- **Скорость:** сокращать время до полного, проверенного результата в целевом репозитории, включая проверку и необходимые исправления.

Результат задаёт цель, качество — условия приёмки, скорость — предмет оптимизации. Набор инструментов, instructions, skills и агентов оценивается по его вкладу в эти цели.

**2026-09-07, подтверждённый запрос пользователя:** провести глубокое исследование технологий, skills, практик популярных LLM-assisted проектов и `opencode-kit`, выбирая улучшения по доказательствам реальной результативности, качества и особенно скорости, без внедрения ради внедрения. После исследования пользователь одобрил направление и попросил создать спеку. Подготовлен [accelerate-verified-delivery](../openspec/changes/accelerate-verified-delivery/proposal.md): технический состав предложения — `project-verification`, `reproduce-regression`, восемь outcome-сценариев, глобальная проверка в двух проектах и отдельная приёмка влияния диагностики. Источники, ограничения доказательств и критерии условных следующих шагов находятся в [дизайне](../openspec/changes/accelerate-verified-delivery/design.md). Пользователь затем поручил реализовать это изменение через `$openspec-apply-change accelerate-verified-delivery`. Реализация и приёмочные сравнения выполняются; количественный выигрыш ещё не подтверждён.

**2026-09-08, уточнение пользователя:** поставляемый набор не должен зависеть от `opencode-kit`; его поддержка и дальнейшие затраты на неё не обязательны. Этот проект использовался как источник идей и изолированный потребитель в проверках, а не как runtime-зависимость навыков. Дополнительные прогоны для него прекращаются; уже полученные результаты сохраняются как исторические свидетельства, без обязательства дальнейшей совместимости. Обязательность повторного измерения ускорения на двух проектах после этого уточнения требует отдельного решения; доказанный количественный выигрыш пока не заявляется.

## Основа — официальный Codex CLI

Основой остаётся официальный Codex CLI с глобальной конфигурацией, skills, агентами, плагинами, MCP и другими подходящими расширениями.

Собственный оркестратор, runtime или изменения самого CLI рассматриваем только при доказанной недостаточности штатных средств расширения для нужного результата. Это направление уточнено и больше не является открытым выбором исходной архитектуры.

## Уровни агентов и реальная эффективность

**2026-09-07, подтверждено пользователем:** цель — реальная экономия лимитов ChatGPT, ускорение полного проверенного результата и автономность. Делегирование оправданно только с учётом постановки, проверки и переделок; его количество не является метрикой успеха. Завершение и качество приоритетны, агент самостоятельно выбирает эффективный способ и обоснованно расходует лимиты.

Уровни универсальны: middle, senior и principal; деятельность определяется заданием и подходящими skills. Grok 4.6 middle всегда приоритетен для подходящего делегирования при доступности. GPT middle на подписке ChatGPT — резерв при недоступности Grok. Senior — Astra xhigh; principal — редкая Astra max консультация по сложному интеллектуальному блокеру. Прямое выполнение, резерв и обоснованная эскалация в согласованной задаче не требуют нового разрешения. `grok_reviewer` заменяется универсальным уровнем. Уточнение пользователя: для всех OpenAI-вызовов использовать только семейство Astra, без GPT-5.*, включая вспомогательные вызовы. Резервный middle — Astra high; приоритетный Grok 4.6 — xhigh (поддержка подтверждена документацией). Технические ограничения и доказательства — в [adaptive-agent-delegation](../openspec/changes/archive/2026-09-08-adaptive-agent-delegation/proposal.md); пользователь поручил создать спеку и сразу реализовать её.

**2026-09-07, повторное отключение при делегировании:** пользователь сообщил о рестарте сессии и предположил недостаточный предел Bun. Результат службы подтвердил остановку по памяти при 768 MiB; это наблюдение, не установленная причина роста. В рамках восстановления агент увеличил только предел службы до 2048 MiB с сохранением containment; административные команды остались на 768 MiB. Проверки и границы вывода — в [отчёте делегирования](evidence/agent-delegation.md). Это новый эпизод после прежнего решения прекратить исследование предыдущего инцидента.

**Наблюдение при приёмке:** на паре коротких функций принудительное делегирование двум Grok увеличило время и расход Astra-родителя. Политика уточнена агентом: объединять связанную рутину и не дробить мелкие задачи. Общая экономия недельной квоты не объявляется доказанной; числа и ограничения сравнения находятся в том же отчёте.

**2026-09-08, подтверждённый запрос пользователя:** устранить пустые завершения Grok, постоянные подгоняющие сообщения и необоснованные переключения на `middle_backup`; отдельно разобраться с сообщениями об ошибках шифрования. Приоритет Grok и привязки Astra сохраняются. Наблюдения, исправления и границы проверки — в [отчёте стабильности Grok](evidence/grok-reliability.md).

- Актуальные указания пользователя определяют дальнейшее обновление этой записи.
