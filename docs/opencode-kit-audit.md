# Аудит идей для дальнейшего переноса из opencode-kit

[Карта документации](README.md) · [Карта переноса](opencode-kit-map.md) · 2026-09-07

Наибольшую ожидаемую пользу сейчас дают проверка поведения инструкций, диагностика действующей конфигурации, повторное использование проверенных проектных знаний и небольшие детерминированные инструменты. Полный перенос runtime opencode-kit имеет высокую цену интеграции и пока не обоснован потребностями harness.

Первичный аудит содержал предложения агента. **Повторная проверка 2026-09-07:** пользователь поручил проверить рекомендации, выбрать первый пакет по ROI, создать и полностью реализовать спеку, заархивировать её и запушить все изменения. Для первой реализации выбрана диагностика источников; [изменение OpenSpec](../openspec/changes/archive/2026-09-07-diagnose-effective-harness-sources/proposal.md). Остальные кандидаты сохраняют статус рекомендаций. [Сверка исходников](evidence/audit-recheck.md) отделяет найденные неточности от уже описанных ограничений.

## Основание и границы доказательств

- Исследован соседний рабочий checkout `../opencode-kit`: HEAD `0e75b94e28f8d860742ef4724f77297e6341630a`, commit от 2026-09-03. На старте `git status --porcelain` содержал 186 строк, включая незакоммиченные и неотслеживаемые пути. Выводы относятся к прочитанным файлам рабочего дерева, а не только к этому commit. Remote не синхронизировался; актуальность относительно GitHub не утверждается.
- Проведены обзор каталогов и выборочная проверка реализации, контрактов и тестов наиболее перспективных механизмов. Это аудит пригодности к переносу, а не полная проверка безопасности всех исходников. Архивные proof-отчёты и название возможности не считаются доказательством её текущей работы.
- Codebase Memory помог найти код, но проверка покрытия сообщила `metadata_changed` для важных файлов. Выводы проверялись по файлам на диске; полнота графа не предполагалась.
- Назначение — официальный Codex CLI **0.153.4** на Windows, Node **24.18.1**. `codex features list` показал `hooks=true`, `multi_agent=true`, `memories=false`. Официальные контракты Codex открыты повторно 2026-09-07. Возможность настройки не означает проверку её будущей интеграции.
- В исходнике обнаружены 35 каталогов skills и 21 Markdown-агент. `global/AGENTS.md` занимает 61 919 байт; глобальная философия harness — 8 436 байт. Это размеры файлов, не стоимость сессии и не измерение качества.
- Ссылки на исходники ниже требуют соседнего checkout с именем `opencode-kit`. Его [MIT LICENSE](../../opencode-kit/LICENSE) нужно сохранить при дальнейшем заимствовании существенных фрагментов кода; сторонние vendored-компоненты требуют отдельной проверки происхождения.

В harness уже поставлены [глобальная установка](installation.md), [MCP/LSP](code-tools-verification.md), [подписки](evidence/subscription-routing-verification.md), [делегирование по уровням](agent-delegation.md) и [исправление таймаутов](evidence/hook-timeouts.md). Они не считаются новыми кандидатами этого аудита. Состояние OpenSpec на старте: 9/9 задач adaptive-agent-delegation, 13/13 connect-subscription-model-routing и 4/4 fix-diagnostic-hook-timeouts; отметки задач сверены с существующими отчётами, но полная приёмка этих поставок заново не запускалась.

## 1. Проверять поведение агента как регрессию

Нужен небольшой набор пользовательских ситуаций с наблюдаемым результатом: простая правка доведена до конца; агент не просит повторно разрешённое действие; P1 воспроизведён и устранён; крупный независимый участок передан middle; недоступный middle не вызывает повторных бесполезных проб; после сжатия контекста сохранены незавершённые требования.

В opencode-kit это направление представлено [consumer-outcome regression](../../opencode-kit/tools/proofs/consumer-outcome-regression.ts), [сценариями consumer-outcome](../../opencode-kit/tools/proofs/consumer-outcome/) и [instruction-context-quality](../../opencode-kit/tools/instruction-context-quality.ts). Заимствовать следует разделение статического соответствия и фактического поведения, фиксацию проверяемого входа, baseline/candidate и явные ограничения доказательств.

Конкретный код для изучения — [evaluate.ts](../../opencode-kit/tools/proofs/consumer-outcome/evaluate.ts): детерминированное сравнение окружения и полей `cleanup`, `forbiddenEffects`, `friction`, `permissions`, `proof`, `validation`; отдельно проверяются privacy markers и digest сценария. При адаптации нельзя терять эти проверки, иначе несопоставимые или раскрывающие приватные данные наблюдения могут пройти оценку. Replay сохранённых наблюдений подтверждает только оценщик; новые наблюдения поведения Codex требуют настоящего запуска. OpenCode-specific live capture и proof-server переносить целиком не стоит.

В harness уже есть [приёмка делегирования](evidence/agent-delegation.md), тесты и учёт расхода. Дополнение — единый небольшой набор регрессий для изменений поведения, а не ещё одна система отчётности. Не требовать дорогого model-backed прогона после каждой правки Markdown. Выбирать сценарии, на которые может повлиять изменение; использовать только Astra для OpenAI и приоритетный Grok для подходящих заданий.

**Проверка пользы:** взять известную неудачную инструкцию и убедиться, что сценарий обнаруживает её реальное последствие; затем проверить исправление в новой сессии вне harness. Записать время до принятого результата, вмешательства пользователя, переделки и расход всех участников. Подсчёт нужных слов в prompt не заменяет этот результат.

## 2. Расширить Check диагностикой действующих источников

Источники: [opencode-runtime-sources.ts](../../opencode-kit/tools/opencode-runtime-sources.ts), [doctor.ts](../../opencode-kit/tools/doctor.ts). Классы доказательств — `config-declared`, `conventional`, `runtime-observed`, `unknown`. Наличие файла в стандартном каталоге не доказывает его загрузку. Есть поиск конфликтов имён и сравнение управляемого OpenCode prompt по hash; этот механизм не подтверждает ревизию уже работающего Codex или MCP/LSP-сервера.

В harness [Check установщика](../tools/kit.psm1) уже проверяет связи и загрузку нового consumer; MCP/LSP и подписки имеют свою диагностику. Первый пакет расширяет эту точку входа: источники настроек и overrides выбранного проекта, дубли skills и целевой файл каждой связи. Нужна проверка поведения именно выбранного профиля: наличие `origins` в app-server API само по себе не доказывает, что API умеет выбрать CLI file-profile. Состояние уже запущенных сессий и серверов остаётся `unknown`, пока нет отдельного наблюдения загруженной ревизии. Нельзя объявлять процесс устаревшим или актуальным по timestamp исходника. Credentials, prompts, полные конфиги и сырые ошибки парсера не выводятся.

**Проверка пользы:** в отдельном временном consumer создать один конфликт skill, один скрывающий override и одну устаревшую связь; получить точную причину и действие восстановления. Вернуть состояние и проверить исчезновение проблемы. Сравнить время диагностики с ручным маршрутом. Полный doctor исходника с его qualification/campaign gates не переносить.

## 3. Запоминать проверенные команды проекта

Источники: [adapters.md](../../opencode-kit/docs/adapters.md), [проектный шаблон](../../opencode-kit/templates/project/AGENTS.md), [init-project.ts](../../opencode-kit/tools/init-project.ts). Полезная деталь — статус команды `confirmed`, `docs-only`, `unknown` или `blocked`, а также предпосылки окружения. Так команда из README не выдаётся за реально выполненную проверку.

Минимальная адаптация: глобальный skill находит существующий проектный источник команд и уточняет в нём проверенные build/test/lint и важные условия запуска. Если такого источника нет, создаётся короткий раздел в подходящем документе проекта. Отдельный JSON-адаптер нужен только при появлении автоматического потребителя. Генератор исходника нельзя запускать как есть: его шаблоны и маршруты принадлежат OpenCode.

**Проверка пользы:** первая сессия определяет и выполняет focused check, вторая после перезапуска использует найденный источник без повторного исследования. Изменившаяся команда должна быть проверена заново. Глобальный skill остаётся нейтральным; конкретные команды принадлежат проекту.

## 4. Настраивать инструкции по месту причины

Источники: [instruction-artifact-tuning](../../opencode-kit/global/skills/instruction-artifact-tuning/SKILL.md), [instruction-context-quality.ts](../../opencode-kit/tools/instruction-context-quality.ts), [инвентаризация инструкций](../../opencode-kit/tools/instruction-artifacts-inventory.ts). Полезен маршрут от конкретного сбоя через фактически загруженный источник к минимальному исправлению и проверке поведения.

Ограничение автоматизации: текущий [seed канонизатора](../../opencode-kit/config/instruction-context-quality.json) содержит одну текстовую замену `in order to` → `to` и явные исключения дубликатов. Это узкий инструмент точных преобразований, не проверка смысла или универсальный оптимизатор prompts. Начинать следует с режима проверки; совпадение текста само по себе не разрешает удалять правило.

Применение к harness: избегать дублирования правил в философии, `developer_instructions`, skill и проектном AGENTS; подробный контракт должен иметь одного владельца. Проверять не только наличие текста, но и достижимость, условия применения и противоречия. Для каждого нового skill нужны подходящий запрос и похожий запрос, на котором он не должен срабатывать. Codex загружает тело skill по необходимости, но каталог метаданных тоже занимает контекст. [Официальный контракт skills](https://learn.chatgpt.com/docs/build-skills).

**Проверка пользы:** воспроизвести лишнее согласование или неверный выбор skill до изменения; проверить исправление и соседний сценарий, в котором прежняя защита всё ещё нужна. Цель — меньше потерь и ошибок, а не минимальный размер текста любой ценой.

## 5. Заимствовать два инструмента для Git-кандидата

[repo-candidate-snapshot.ts](../../opencode-kit/global/bin/repo-candidate-snapshot.ts) собирает HEAD, историю, staged/unstaged/untracked/conflict paths, upstream и ограниченные patches. Результат явно сообщает truncation. Он полезен для передачи точного состояния reviewer и предотвращения повторного набора команд. Это read-only helper; недостаточный размер вывода должен вести к адресному чтению, а не к выводу о полноте ревью.

[validate-staged.ts](../../opencode-kit/global/bin/validate-staged.ts) строит tree из index, создаёт технический commit без перемещения ветки, запускает переданный validation argv в отдельном worktree и убирает его. Содержимое рабочего дерева пользователя не становится проверяемым кандидатом. Сопутствующий [portable-process.ts](../../opencode-kit/global/bin/portable-process.ts) решает реальные особенности Windows argv, `.cmd` и завершения процессов.

Минимальный перенос: общий снимок плюс явная команда проверки staged-кандидата перед поставкой, когда есть риск расхождения index/worktree. Не выполнять на каждом tool call. Учесть зависимости helper, побочные Git objects/worktree metadata, cleanup при ошибке и изменении index между проверкой и поставкой. `--reuse` создаёт связи с ignored-каталогами исходного проекта: это не полная изоляция; mutable caches и state требуют отдельной политики.

**Проверено в аудите:** 11 тестов snapshot и 5 выбранных staged/argv тестов прошли. В том числе index с проходящим содержимым при отличающемся рабочем файле, сохранение ошибки дочернего процесса, cleanup, Windows executable с пробелами и буквальная передача аргументов. Эти проверки подтверждают исходные helpers на данной машине, а не установленную возможность Codex.

## 6. Перенять контракт памяти, затем выбрать механизм

Источники: [project-memory.md](../../opencode-kit/docs/project-memory.md), [recall.ts](../../opencode-kit/global/plugin/project-memory/recall.ts), [store.ts](../../opencode-kit/global/plugin/project-memory/store.ts), [records.ts](../../opencode-kit/global/plugin/project-memory/records.ts), [интеграция hooks](../../opencode-kit/global/plugin/project-memory/index.ts).

Ценные свойства: явные candidate/promote/invalidate; ссылки на доказательства; fingerprint исходника при подтверждении; отсечение изменившихся или пропавших источников; ограниченный объём recall; изоляция canonical worktree; память уступает текущим требованиям и коду. В исходнике 180 дней — предельный возраст подтверждения, а не гарантия истинности. Документация описывает предел advisory context 8 КиБ и до семи выбранных записей. Значения не стоит переносить без измерения.

Сначала использовать уже принятый `docs/project-decisions.md` для решений и проектные документы для проверенных процедур. Затем сравнить native memories с явным retrieval из этих источников. Codex имеет отдельное локальное хранилище памяти, фоновые извлечение/консолидацию и настройки моделей; обязательные правила официальная документация рекомендует держать в AGENTS или tracked docs. В текущем CLI память выключена. [Memories](https://learn.chatgpt.com/docs/customization/memories), [настройки моделей памяти](https://learn.chatgpt.com/docs/config-file/config-reference).

Перед экспериментом с native memories явно назначить Astra для extraction и consolidation, проверить фактическую модель, расход и изоляцию проектов. Не считать фоновую память бесплатной и не предполагать эквивалентность fingerprint-политике исходника. Собственный store оправдан, если на реальном сценарии штатный механизм не закрывает существенное требование.

**Проверено в аудите:** 9 тестов исходной памяти прошли: отключённый режим без IO, lifecycle, freshness/evidence exclusions, Serena read-only recall, изоляция roots, конкурентное выделение последних slots. **Проверка будущей пользы:** в новой сессии найти подтверждённую процедуру, затем изменить её evidence-файл и убедиться, что старый совет не применяется; проверить соседний проект и стоимость повторного исследования.

## 7. Выбирать короткие инженерные skills по реальному спросу

Наиболее универсальные кандидаты: [root-cause-analysis](../../opencode-kit/global/skills/root-cause-analysis/SKILL.md) и [openspec-consistency-review](../../opencode-kit/global/skills/openspec-consistency-review/SKILL.md). Первый различает симптом, непосредственный триггер, несработавшую защиту, причину и `unknown`, требует проверить альтернативные объяснения. Второй сверяет proposal/design/spec/tasks/docs/tests и доказательства закрытых задач. При адаптации сверять весь принятый объём: исходная терминология «next increment» не должна ослабить критерий пользователя о выполнении всей спеки. Отдельные доказательства улучшения поведения этих двух skills в Codex не получены.

[config-schema-validation](../../opencode-kit/global/skills/config-schema-validation/SKILL.md) в основном повторяет общий checklist, поэтому отдельный перенос имеет меньший приоритет. Полезнее изучить [валидатор конфигурации](../../opencode-kit/tools/validators/opencode-config.ts) и проверки структуры skills/agents, затем расширить существующие проверки harness по актуальному контракту Codex. Общие принципы воспроизведения, проверки и честного завершения уже есть; новая детализация должна решать наблюдаемый пробел.

Деятельность задаётся skill и заданием существующему middle/senior/principal. Создавать отдельную модельную роль для каждой профессии не требуется. Официальный Codex поддерживает пользовательских субагентов, но само число агентов не является доказательством выигрыша. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Предметный резерв: [legacy-contract-extract](../../opencode-kit/global/skills/legacy-contract-extract/SKILL.md), [framed-protocol-implementation](../../opencode-kit/global/skills/framed-protocol-implementation/SKILL.md), [wire-protocol-golden-tests](../../opencode-kit/global/skills/wire-protocol-golden-tests/SKILL.md), [external-service-simulator-harness](../../opencode-kit/global/skills/external-service-simulator-harness/SKILL.md), [windows-service-packaging](../../opencode-kit/global/skills/windows-service-packaging/SKILL.md), [latency-benchmark-pack](../../opencode-kit/global/skills/latency-benchmark-pack/SKILL.md). Это кандидаты каталога; глубокая проверка всех этих skills и их production-потребителей в аудит не входила.

**Проверка пользы:** выбрать один повторяющийся тип работы, адаптировать один целостный skill с ресурсами и испытать в реальном проекте. Для consistency-review подойдут корректный архивный change и временный пример с рассинхроном tasks/spec; для root-cause — уже документированный инцидент с известной границей доказательств. Проверить также похожую задачу, которой skill не нужен. Не устанавливать весь каталог заранее.

## 8. Взять минимальный цикл Kaizen

Источники: [complain](../../opencode-kit/global/skills/complain/SKILL.md), [kaizen.md](../../opencode-kit/docs/kaizen.md), [store.ts](../../opencode-kit/global/plugin/kaizen/store.ts), [controller.ts](../../opencode-kit/global/plugin/kaizen/controller.ts). Хорошая идея — одна короткая запись наблюдаемой проблемы с evidence, влиянием и статусом; повторная запись дедуплицируется; сбор не блокирует задачу. Ошибка с неизвестным результатом записи не порождает второй экземпляр через fallback.

Для harness уже есть наблюдаемые кандидаты: таймауты диагностики, разрыв текущей сессии при lifecycle-проверке, невыгодное дробление маленькой задачи. Начать можно с небольшого общего журнала в kit и тематических evidence-документов. Исправления остаются обычными согласованными изменениями. Автоматический анализ всех transcripts, отдельные compaction-envelopes, SQLite migration, leases и dispatch-контроллер для первого шага не нужны.

Конкретная граница исходной документации: `docs/kaizen.md` описывает inbox, но в текущем `store.ts` есть выбор SQLite v2 при `OPENCODE_KAIZEN_DATA_DIR`; также присутствуют grind/controller-модули. Копирование operator guide целиком не даст полного контракта текущего runtime.

**Проверка пользы:** один повторный сигнал не создаёт дубликат; исправление связано с исходной проблемой; на следующих сопоставимых задачах проверено, исчезла ли потеря времени. Частота жалоб сама по себе не определяет приоритет и не разрешает автоматическую правку глобальных инструкций.

## 9. Сохранять прогресс без второго оркестратора

Источники: [session-delivery-context](../../opencode-kit/global/plugin/session-delivery-context/), [session-completion-guard](../../opencode-kit/global/extensions/session-completion-guard.ts), [work-campaign](../../opencode-kit/global/bin/work-campaign.ts), [стратегическая карта](../../opencode-kit/docs/self-evolving-development-system-roadmap.md). Полезные идеи — различать пользовательские и синтетические сообщения, хранить незавершённый результат и следующую проверяемую попытку, учитывать фоновые работы и честно фиксировать блокер.

Guard напрямую зависит от OpenCode v2 session APIs и общего PTY manager. Campaign/Mission добавляют writer ownership, durable transitions, reconciliation и supervisors. Это существенная самостоятельная система, а не перенос одного prompt. В harness уже есть OpenSpec, native subagents и hooks; Goals документированы как устойчивый контракт задачи в рамках thread. [Using Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex).

Минимальное направление — короткое сохранение оставшейся работы в owning change и проверка восстановления с native resume/Goals, когда пользователь выбрал Goal. Stop hook может инициировать продолжение, но это отдельный эффект; PreCompact/PostCompact имеют свои контракты и не эквивалентны OpenCode `output.context`. [Hooks](https://learn.chatgpt.com/docs/hooks).

**Проверка пользы:** compaction, остановка пользователем и перезапуск сохраняют согласованную цель и незакрытые требования; завершённая задача не продолжает расходовать модели; пользовательская остановка соблюдается. Свой runtime рассматривать после конкретно воспроизведённого недостатка штатного пути.

## Что не переносить целиком

| Исходный элемент | Причина | Полезная часть |
| --- | --- | --- |
| Большой глобальный AGENTS и все 35 skills | Рост постоянного контекста, пересечения и цена выбора | Короткое ядро и тематические ресурсы |
| 21 профессиональная роль и исходные model profiles | Конфликт с принятыми универсальными уровнями и Astra-only | Контракт задания, review-приёмы и предметные skills |
| Generated `.runtime-profiles` и копирование конфигурации | Пользователь выбрал прямое чтение исходников через ссылки | Preview состава, поиск конфликтов и проверка загрузки |
| Полные qualification/RC/SDET gates на каждую задачу | Ненужная цена на малых изменениях; уже выбраны проверки по спеке и риску | Сценарии реальных критических отказов |
| Kaizen grind, Beads, Campaign/Mission как обязательный слой | Пока нет доказанного спроса на такой объём управления состоянием | Неавторизующая запись проблем, изоляция writers, восстановление |
| Автоматический перенос TypeScript OpenCode plugins | Несовпадение событий, SDK, discovery и lifecycle | Алгоритмы с явными входами плюс новый Codex-адаптер |
| Проверка инструкций только по строковым маркерам | Текст может содержать нужные слова и давать неверное поведение | Статика для структуры, отдельный сценарий для поведения |

## Практический следующий шаг

Для первой реализации выбран **Check с диагностикой источников**: он использует существующий lifecycle, помогает при уже наблюдавшихся проблемах глобальной загрузки и не требует модельных прогонов. Это ожидаемый максимальный ROI по текущему спросу и стоимости адаптации, а не измеренное сравнение всех кандидатов. Команды проекта и поведенческие регрессии остаются следующими самостоятельными пакетами; отсутствие исходного корпуса сценариев учитывается в цене регрессий. Затем — Git helpers и один skill расследования; память и Kaizen — после сравнения с простыми существующими средствами.

При реализации каждого выбранного пакета результат включает глобальную регистрацию через lifecycle harness, сохранение пользовательских настроек, проверку из другого проекта и обратимое отключение. Одних файлов в checkout недостаточно. Статус первого пакета определяется его OpenSpec-задачами и отчётом приёмки; остальные предложения не объявляются поставкой.
