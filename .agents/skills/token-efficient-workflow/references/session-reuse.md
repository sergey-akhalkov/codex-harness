## Repeated preparation and sessions

When setup or feedback waits dominate, use the next unresolved fact to choose a smaller verifiable operation; `project-verification` owns failure attribution and the check. Compare continuing valid owned state, returning it to a known starting state, and restarting the minimum necessary component. One permanent session is not the goal: restart when it is cheaper, more reliable or required to restore the relevant condition. Reuse unaffected preparation. Learn uncertain interactions through individual observed actions and return paths, then exercise their code through the existing automation owner on the same valid state. Keep preparation separate from replay where supported. Inspect an existing step/attach path before adding a helper; do not build general automation for a short task.

Keep a usable prepared resource available for the next authorized observation when its state and ownership permit it. Do not trade required isolation or restoration for reuse. While a long invocation is pending, prefer available phase/error evidence or independent work over repeated status-only polling; a wait on that invocation is not another attempt. Waiting for necessary recovery is legitimate, but report the known primary failure without waiting solely for the final receipt. If progress is unavailable, state that limitation instead of counting process existence as a useful signal.

Reuse requires current relevant inputs and runtime conditions. After interruption, a changed build/configuration/input or an ended session, re-establish affected preconditions and checks while preserving unaffected knowledge. A substitute diagnostic host must preserve the real entry point's relevant conditions before its result can be consumed. Keep commands, validity conditions and useful findings in the project's existing memory home, with private state and evidence outside shared sources. A local helper pass leaves parent acceptance pending until its result is consumed and checked.

Invest incrementally in the current path. Compare expected savings over the remaining repetitions with implementation, validation, integration and recovery cost. Use existing timing evidence first; measure setup, useful action, observation or recovery separately only when uncertainty could change the decision. Count briefing, worker effort and rework as costs, and overlapping wall time only once. Mark estimates as estimates; fewer launches or smaller output alone do not prove faster completion. A plainly cheaper direct action needs no numeric budget, recurring timer, new report or separate specification.

When delegation is available, authorized and worthwhile, give a worker a bounded missing fact or correction and name the parent decision or integration point that will consume it. The parent continues independent work, uses decisive findings when available and revisits assignments whose premises have changed. Finding a supported observation path can shorten the current task; unrelated polish, duplicate investigation and a permanent efficiency monitor do not earn that cost. Preserve conversation visibility, one owner for shared runtime resources and aggregate resource limits. If those conditions cannot be met, take the cheaper permitted direct path.
