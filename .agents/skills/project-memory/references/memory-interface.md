# Optional Serena interface

Keep each fact in its existing project owner. A Serena entry may point to that
owner; it must not copy the decision and become a competing authority. A new
topic may have one Markdown owner in `.serena/memories` only when the project
selects that layout. Link it from the ordinary project index and check that Git
includes the actual file. Native file tools and a fresh clone must still work
without Serena, personal history or a running service.

The compared selection is `retain-native`. Native file and Git operations completed
the same decision, stale-command, rename and both-reference tasks. Serena 1.7.0
reads worked, but `edit_memory` and `rename_memory` were rejected under the
durable `approval_policy=never` comparison contract. Do not adopt Serena as the
maintenance path for that reason. Count extra listing/pointer reads and recovery,
not only the short tool result. Do not create pointers for every document merely
to exercise an optional interface. Existing records replace repeated onboarding;
if `memory_maintenance` is used, point it to the owning project rules instead of
maintaining another policy copy.

The qualified Serena 1.7.0 interface uses project memory names for `read_memory`
and `write_memory`; it does not read an arbitrary docs path through those calls.
Project `read_only_memory_patterns` blocks matching tool writes, while
`ignored_memory_patterns` hides matching entries and rejects memory-tool reads
and writes. These controls do not restrict separately authorized native tools.
Use synthetic owned entries when qualifying another version or configuration.

`rename_memory` updates `mem:` references; ordinary Markdown links need their
own check and repair. Do not assume a successful rename covered every format or
that a failed rename left files untouched. In the qualified implementation the
owner moves before the reference scan: a locked reference file can cause an
error after the move. Inspect both old/new paths and affected references, retain
unrelated edits, then complete or roll back only the unfinished operation.
Check protected references separately; never remove protection to make a rename
appear successful.

Before a portability claim, inspect ignore rules and the exact committed fixture
revision, then read the files from a fresh clone. Keep runtime caches out of Git.
For conflicting worktrees, preserve both versions and evidence until the current
user decision and source facts resolve the owner; a tool's successful write is
not conflict resolution. Kit disconnect must leave project knowledge in place.
