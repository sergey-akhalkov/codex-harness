## Choose the feedback boundary

Use this section when verification is slow, inconclusive or fails before the intended behavior. At an informative tool result or observed stall, check whether uncertainty about the accepted result decreased. Different locator, dispatch and readback errors can all expose the same unlearned driving stage. Before another consequential repeat, name the missing fact and choose an observation that distinguishes the plausible causes: what would each outcome change next? If every outcome leads to the same action, reconsider whether the observation is useful. A new error or added diagnostic alone does not justify full preparation. Make the changed method visible in the next applicable actions; a cheap understood correction needs no helper, worker, report or separate specification.

Establish whether preparation, driving, the product action, observation or restoration failed. A driver failure before the action leaves the product untested. If an action appears to succeed but its observer rejects it, preserve that evidence and investigate the observer's conditions separately; visible movement alone does not establish the downstream result. Use `reproduce-regression` for an actual CLI/MCP/process regression within its scope, preserving the original trigger. Refresh understood stale dependencies through their existing preparation path.

For unfamiliar interactions, inspect the current owned state, perform one bounded permitted action, observe its effect and learn the required return path. This can be direct browser/desktop interaction, an individual CLI operation or an MCP request; it does not require the user to drive or a whole unattended script written before the route is understood. For UI work, inspect the relevant owned windows, including a blocking dialog when the main-window image cannot explain the failure. Check the actual postcondition, not just successful dispatch. Exercise the corresponding production automation function against the same valid state, then integrate it and complete the parent check. A separate recipe remains intermediate evidence. Do not edit a held or identity-bound artifact underneath an active operation; use a permitted separate candidate and integrate after release and revalidation.

Give a smaller check explicit inputs, required state and a parent consumer. Inspect existing step, attach, inspection or observation support before declaring that the full path is necessary or adding another mechanism. Make a bounded improvement in the existing owner when authorized and worthwhile; otherwise state the concrete limitation and pursue independent work. Compare a reduced host with the actual entry point's relevant configuration, observation and recovery conditions. If only a full run retains the required startup, timing, reset or integration condition, identify that dependency and run its unchanged assertions. Preserve explicit user method choices and reject a passing reduction that removed the question.

While a run or its supervisor remains pending, use available phase/error evidence to resolve the next decision, or do independent authorized work. Report the original failure separately from incomplete cleanup; process existence and repeated waits are not a new result or launch. Do not interrupt necessary recovery merely to shorten a wait. An interrupt request is not proof that tools stopped. Preserve unknown cause or recovery status when evidence is unavailable, identify the owning observation gap and finish required restoration before conflicting interaction. Increasing a timeout does not repair a missing observation.
