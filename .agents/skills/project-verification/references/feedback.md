## Choose the feedback boundary

Use this section when verification is slow, inconclusive or fails before the intended behavior. Before a consequential repeat, identify the unresolved fact, the observation that distinguishes alternatives and the smallest operation preserving the relevant conditions. A different error or additional diagnostic is not sufficient reason to repeat full preparation. Make a changed method visible in the next applicable actions; a promise to switch is not progress. A cheap understood correction needs no new helper, worker or per-command report.

Establish whether preparation, driving, the product action, observation or restoration failed. A driver failure before the action leaves the product untested. If an action appears to succeed but its observer rejects it, preserve that evidence and investigate the observer's conditions separately; visible movement alone does not establish the downstream result. Use `reproduce-regression` for an actual CLI/MCP/process regression within its scope, preserving the original trigger. Refresh understood stale dependencies through their existing preparation path.

For unfamiliar interactions, use available tools to inspect the current owned state, perform one bounded permitted action, observe its effect and choose the next action. This can be direct browser/desktop interaction, an individual CLI operation or an MCP request; it does not require the user to drive or an unattended script written before the route is understood. Cover only required transitions and relevant return paths. Verify understood actions through the existing automation owner on the same valid state where feasible, then complete the parent check. An exploratory recipe remains intermediate evidence.

Give a smaller check explicit inputs, required state and a parent consumer. Inspect existing step, attach, inspection or observation support before adding a missing path. Make a bounded improvement in the owning mechanism when authorized and worthwhile; otherwise state the concrete limitation and pursue independent work. Preserve explicit user method choices. If only a full run retains the relevant startup, timing, reset or integration conditions, identify that dependency and run its unchanged assertions. Reject a passing reduction that removed the question.

When an application exits or a supervisor remains pending, inspect available phase/error evidence and restoration progress. Report the original failure separately from incomplete cleanup; process existence and repeated waits on the same invocation are not a new result or another launch. An interrupt request is not proof that tools stopped. Preserve unknown cause or recovery status when evidence is unavailable, identify the owning observation gap, and finish required restoration before conflicting interaction. Do not infer that increasing a timeout fixes a missing observation.
