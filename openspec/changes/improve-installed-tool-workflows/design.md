## Context

Мотивация и согласованный объём — в [proposal.md](proposal.md). Design нужен из-за пересечения памяти, инструментов, глобального lifecycle и оценки производительности.

Исследование 2026-09-08 наблюдало Codex CLI 0.153.4 и 86 операций четырёх локальных MCP: Serena 1.7.0, Codebase Memory 0.10.8, Graphify 0.9.55, Nuphus 0.2.2. `get_current_config` подтвердил проект harness и LSP Python/Rust; overview работал для `tools/code-tools/serena_proxy.py` и `crates/harness-core/src/lib.rs`. `list_memories` вернул `{}`; onboarding отсутствовал. Graphify с явным корнем harness вернул `graph.json not found`; Nuphus перечислил `about:blank`. Это наблюдения отдельных read-only операций, а не приёмка всех функций или скорости.

CBM project/status указали правильный root и 18 частично разобранных PowerShell-файлов. Индекс в исследовании не обновлялся, поэтому его текущая полнота не подтверждалась. Выборка запросов 12 сессий была эвристическим основанием гипотез; она не является benchmark или измерением квоты.

Проверенные owning records: [code tools](../../../docs/code-tools.md), [Serena qualification](../../../docs/code-tools.md), [token workflow](../../../docs/token-workflow.md), [Git memory](../../specs/git-project-memory/spec.md), [resource policy](../../../global/tool-resources.json). Предыдущие проверки переиспользуются только при совпадении существенных source/runtime/dirty inputs. Состав поддерживаемых языков не расширяется автоматически из каталога возможностей.

## Goals / Non-Goals

**Goals:** получить проверенные короткие маршруты для типовых вопросов, доказательно выбрать опциональные интерфейсы и обеспечить их обычное применение вне harness. Сохранять полноту результата, актуальность данных и восстановление после ошибки.

**Non-Goals:** новый диспетчер инструментов, постоянная телеметрия сессий, база памяти, синхронизация хранилищ, обязательная миграция всех знаний, новое обучение skills, восстановление контекстных/диагностических хуков, включение всех языков или замена текущих подписок. MCP-based запрет записи не объявляется полноценной песочницей для других инструментов Codex.

## Decisions

### 1. Один короткий маршрут и подробности по требованию

Расширить существующий `token-efficient-workflow` необходимыми маршрутами и ссылками на небольшие тематические references; `project-memory` сохраняет правила владения и актуальности. Глобальные инструкции содержат только выбор маршрута и важные инварианты. Не создавать отдельный skill на каждую MCP-команду, не копировать целиком upstream manuals и не внедрять принудительный scheduler. Альтернатива большой постоянно загруженной инструкции отклонена из-за контекста и риска расхождения версий.

| Задача | Предпочтительный путь при выполненных prerequisites | Ограничение и запасной путь |
| --- | --- | --- |
| Влияние diff | CBM `detect_changes`, затем нужные consumers и проверки | Свежий индекс, точный diff/base и coverage; динамические потребители требуют дополнительной проверки |
| Архитектура области | CBM `get_architecture` с нужными aspects/path | Не запрашивать весь граф; подтвердить существенные связи исходниками |
| Источник значения и цепочка вызовов | CBM `trace_path` с подходящим mode; Serena references/definitions | Отсутствующие связи не доказывают отсутствие runtime пути |
| Поиск по смыслу | CBM semantic search только при соответствующей генерации | Проверить релевантность; fast index не означает готовность semantic edges |
| Точный символ и изменение | Serena overview/definition/references, затем подходящий edit либо `apply_patch` | `relative_path`, `max_matches`, тела только при необходимости; проверяется поведение вызывающего entry point |
| Браузерная последовательность | Nuphus scoped snapshot, стабильные refs, `browser_exec` | Пакет до ближайшей смысловой развилки; результаты шагов и конечный эффект проверяются отдельно |
| PR/diff/CI или документ | Соответствующая connected App | Проверить remote identity либо session/schema; отсутствие подключения не запускает установку или внешнюю запись |

CBM index refresh происходит перед первым graph-backed запросом при неизвестной свежести и после изменений перед следующим запросом. В неизменившейся группе запросов generation переиспользуется; при busy/failure/read-only scope используется свежий доступный источник с явным ограничением. Автоматические index/watch остаются выключенными. Python/Rust являются наблюдавшейся поддержкой, другие языки квалифицируются только по потребности конкретного проекта.

### 2. Память: выбор интерфейса, сохранение владельца

Baseline — существующий маршрут `AGENTS.md -> docs/memory/README.md -> owning records`. Candidate — Markdown-память Serena с теми же фактами, областями применимости и проверками. Для существующих документов candidate сначала использует небольшой указатель на owning records без копирования содержимого. Для новых изолированных тем допускается один авторитетный файл в `.serena/memories/` с обычной ссылкой из проектного индекса; он остаётся доступен native file tools.

Не предполагать, что Serena автоматически читает произвольный `docs/memory`: её текущий интерфейс работает с собственной памятью. `mem:` rename/check обслуживает только такие ссылки; обычные Markdown-ссылки проверяются отдельно. Symlink/sync adapter не является обязательным решением. Уже существующие записи не переносятся до принятия candidate; перенос, если потребуется, сохраняет ссылки, Git review и откат. Глобальные факты/секреты не выносятся из проекта в личную память Serena. Расположение нового уникального topic в candidate проверяется только в owned fixture и не выбирает рабочее хранилище заранее. Проверка ignore/tracked состояния обязательна: untracked запись допустима как незакоммиченная рабочая правка, но её переносимость не подтверждена, пока commit owned fixture и свежий clone не содержат эту запись. Ignore исправляется только scoped способом; runtime cache не попадает в Git.

Сравнение включает выбор темы, устаревшую команду, новое решение, отсутствие нового знания, rename/битую ссылку, свежий clone без истории/MCP и конфликт двух worktrees. В owned фикстурах проверить topic listing, явные reads, read-only/ignored patterns и отказ записи. Onboarding не запускает повторное широкое изучение уже описанного проекта: текущие records читаются выборочно. `memory_maintenance` используется только после согласования с existing skill; второй набор расходящихся правил не создаётся.

Результат выбора: `adopted` с обозначенной областью либо `retain-native` с причиной. Отсутствие преимущества или нарушение переносимости оставляет baseline. Даже при `retain-native` обязательны исправленные маршруты, документированный выбор и внешняя проверка; это не разрешение пропустить сравнение. Данная возможность дополняет, а не закрывает [git-project-memory](../../specs/git-project-memory/spec.md).

### 3. Дополнительные возможности с конечной областью оценки

**Graphify:** один owned пример со связями реализации, конфигурации и документированного правила; независимо известный ответ сравнивается с CBM + прямыми документами. Синтетический граф проверяет identity/query, но преимущество построения графа требует фактического extraction/update из исходных файлов. В стоимость входят создание, актуализация и чтение. Если текущий доступный локальный путь не создаёт нужные связи, фиксируется `retain-current` с причиной; скрытый model/API вызов, скачивание или новая подписка не допускаются. Отдельный бессрочный graph-maintenance процесс не вводится.

**Serena query-projects:** сравнить чтение двух известных символов в двух owned roots с текущим broker/activation. LSP-вариант требует штатного Project Server; сначала проверить установленный контракт и ресурсы. Disposable запуск допустим только после подтверждения ownership/cleanup; он не становится глобальной службой автоматически. При отсутствии полезного выигрыша или несовместимости с лимитами сохранить текущий путь. Глобальная поставка нового сервиса требует конкретного lifecycle/rollback в рамках этого change; отсутствие такого безопасного пути означает отклонение candidate, а не обход лимитов.

`manage_adr`, ingest runtime traces, JetBrains backend и внешняя vision-модель не выбираются: текущая потребность закрывается owning records и существующей навигацией/проверками. Их добавление потребует отдельного конкретного consumer, которого этот change не изобретает.

### 4. Проверить инструкции и выбранные режимы по фактическому поведению

Наблюдавшийся `initial_instructions` предлагает чрезмерно доверять успеху рефакторинга; сохранённая диагностика Serena не гарантирует свежий clean при пустом ответе. В поставляемом маршруте явно сохраняются проектные проверки и границы evidence. Предпочтение — supported Serena context/mode configuration или одна краткая owning инструкция; vendor patch и повторное копирование manual не являются исходным решением.

В Serena 1.7.0 файл `planning.yml` перечисляет не все современные edit tools. Для выбранного read-only MCP-профиля использовать проверенные supported ограничения и actual tool list, а не только название режима; отрицательные вызовы на owned target обязаны оставить его bytes неизменными. Профиль не переключается через недоказанный native API в середине turn. Проверить состав уже созданной сессии отдельно от нового consumer; metadata объявления не доказывают effective behavior.

`initial_prompt` по умолчанию остаётся пустым либо содержит только короткий указатель. `embed_memory` и полный onboarding не применяются для постоянной загрузки всех знаний. Tool allow/deny lists включаются лишь при подтверждённой необходимости и сохранении fallback; уменьшение числа exposed tools не считается самостоятельным доказательством экономии.

### 5. Формирование выдачи и сравнение результата

Использовать текущий Code Mode: независимые calls через `Promise.allSettled`, результаты анализируются до `text()`. Для MCP выбирается одно достаточное представление; transport rejection, `isError`, nonzero exit, truncation и отсутствие данных сохраняются явно. В details остаётся исходный результат с идентификатором источника. Чистое извлечение полей не меняет смысл ответа; raw locator/session store не объявляется постоянным evidence.

Не вводить жёсткий общий лимит, молча обрезающий полезный ответ. Сначала ограничивать scope/поля/page size; при превышении возвращать признак неполноты и путь к продолжению. Для sequential browser шагов сохранять исходы выполненных действий; после частичного успеха не повторять весь пакет. Скриншоты сохраняются для визуальных свойств, текстовые снимки — для доступных элементов.

Для сравнения переиспользовать подходящие части существующих [outcome checks](../../../docs/rust-native.md#outcome-usage-and-helpers) и [token evidence](../../../docs/token-workflow.md), без нового evaluation framework и без переноса исторического вывода о пользе на новые inputs. До первого запуска зафиксировать scoped source/dirty/runtime identities, независимый oracle, allowed effects, измеряемые размеры, приемлемую малую потерю времени и число/условия дополнительных пар. Порог нельзя менять после просмотра результата ради принятия candidate.

Решение принимается по следующим правилам:

- Все обязательные oracle и meaningful failure cases проходят; качество не обменивается на токены. Обнаруженный P0/P1 устраняется до принятия пути.
- Для повышения эффективности должен быть наблюдаемый выигрыш времени либо контекста сверх вариации; допустимая малая потеря другого измерения заранее ограничена и не допускает материального ухудшения скорости согласно действующему контракту. Без этого baseline сохраняется, а полезность не утверждается.
- Сначала одна native baseline/candidate пара на законченный эпизод. Повтор нужен для маршрута, на основании которого выбирается более эффективный путь или заявляется повторяемая польза, либо для конкретной неоднозначности; в таком случае получить минимум две пары с чередованием порядка. Одна пара может обосновать сохранение baseline, но не выигрыш сверх вариации. Результаты всех попыток, ошибок и исправлений сохраняются. Бессрочного добора удачного результата нет.
- Сравнение держит одинаковыми задачу, существенные inputs, модель/effort, выбранные capabilities и oracle. Cold/setup расходы отделяются от warm reuse, но входят в стоимость первого результата. Делегирование и review/rework учитываются. Только Astra используется для OpenAI assignments, preferred Grok сохраняется; вспомогательные model calls не создаются ради счётчиков.
- Измеренные токены, оценка токенов, bytes/chars, время и квота — разные поля. Если native usage недоступен, это явно неизвестное значение; локальное сокращение ответа не превращается в процент недельной экономии.

### 6. Конечная матрица приёмки

Каждая строка получает фактический результат и ссылку на evidence. Детерминированные protocol/oracle проверки используются до модельных эпизодов; один native эпизод может покрыть несколько связанных строк. Весь набор не требует отдельного child на каждую команду.

| ID | Сценарий | Независимое свидетельство и граница |
| --- | --- | --- |
| C1 | Diff затрагивает вызывающий код; данные проходят через несколько функций | Known caller/value oracle, actual CBM operations, точный diff, реальный entry point; stale/partial graph не выдаётся за полный |
| C2 | Архитектура области и похожая реализация с другим именем | Известные source relationships; scoped architecture/semantic запросы, нерелевантные совпадения отброшены; недоступный semantic mode имеет проверенный fallback |
| S1 | Малый рефакторинг и изменение тела, включая ошибочный тип/поведение | Actual Serena read/edit, caller check и native check; `OK`/пустая диагностика не закрывают oracle |
| S2 | Выбранный read-only MCP-путь и режим после нового запуска | Actual tool discovery + попытки разрешённой и запрещённой операции; bytes owned target и сохранённый native write path соответствуют полномочиям задачи |
| O1 | Независимый batch: success, MCP error, process failure, oversized result | Все outcomes различимы, детали доступны без повторного выполнения; не скрывается partial coverage |
| M1 | Решение/устаревшая команда/нерелевантная тема/нет нового знания | Одинаковый answer oracle для native и Serena candidate, одна owning запись, нерелевантные тела не читаются |
| M2 | Rename, read-only/ignored entry, сломанная ссылка, partial write, ignore/untracked, clone и worktree conflict | Проверки обоих типов ссылок, отказ/восстановление, сохранность данных/обеих версий; запись действительно включена в clone и читается без личной истории и без Serena |
| B1 | Форма в owned странице, semantic checkpoint и ошибка после успешного шага | DOM oracle и step outcomes; нет слепого replay уже выполненного эффекта; scoped snapshot сохраняет нужные controls |
| G1 | Code/config/docs question, затем source update или чужой/отсутствующий graph | Известный ответ, время подготовки/актуализации; граф явно выбран и не подменён default graph другого проекта |
| Q1 | Два roots с одинаковыми именами символов | Ответ соответствует каждому root; измеренные процессы/cleanup либо обоснованный отказ до запуска неподходящего пути |
| A1 | Matching App read и отсутствие ресурса | Для доступного подключения — actual read и identity; отсутствующая session/access отмечены, внешние записи не выполняются |
| E1 | Raw/native baseline и optimized законченный эпизод | Один oracle, зафиксированные inputs/model/effort, predeclared tolerances, время/размер/доступные токены и явная неопределённость квоты; setup/errors/rework учтены, положительный выбор поддержан повторением |
| L1 | Глобальные consumers и lifecycle | Native prompt input из двух outside roots, один с локальными AGENTS; parent и named child применяют подходящие маршруты; install/update/relocation/disconnect/rollback сохраняют данные и чужие настройки; policy не выдаётся за принудительный scheduler |

C1/S1/O1 и B1 объединяются в короткие соответствующие native code/browser эпизоды; M1/M2 составляют эпизод памяти. E1 обязателен для сравниваемых маршрутов. G1/Q1 — обязательные конечные оценки кандидатов: без evidence-backed `adopted`/`retain-current` они остаются открытыми, хотя принятие дополнительных путей условно. A1 требует реального read, если подходящая App и ресурс доступны; тогда одной discovery недостаточно. Проверенное отсутствие доступа/session является достаточным negative path, а не заявлением о работоспособности remote operation; неизученная доступность оставляет A1 открытым. Непрохождение обязательного C/S/O/M/B/E/L oracle остаётся открытой задачей.

### 7. Владение и согласование со связанными изменениями

- `adopt-project-memory-and-native-workflows` владеет базовой памятью, context pilot, worktree и structured exec. Текущее evidence: Git-память 1.3/1.4 принята в независимом fixture, свежем clone и конфликте двух worktrees; Astra runtime pilot 2.1 и ordinary runtime/false override/profile rollback 2.2 приняты. Общая lifecycle-приёмка глобальных навыков также пройдена и сведена в [текущих решениях о native workflows](../../../docs/project-decisions.md#native-workflows). Этот change добавляет только выбор интерфейса памяти и использует готовые элементы; не объявляет недостающую приёмку выполненной. Нужные memory prerequisites проверяются до M1/M2; остальные ветви не блокируют независимые C/S/O/B работы.
- `autonomous-skill-evolution` владеет извлечением/проверкой/публикацией skills и session awareness. Owned probe 1.1 доказал current-session skill delivery через hook additionalContext на startup/resume/manual/automatic compact. Глобальная политика это запрещает: ordinary diagnostic/context/Stop hooks остаются OFF, кроме узкого RTK-исключения. Same-session compact/resume delivery без этих хуков остаётся owning blocker; требования не снижаются и не закрываются. Настоящее изменение не возвращает хуки и не обещает закрыть этот контракт.
- `accelerate-verified-delivery` владеет своими outcome cases и прежними benefit claims. Переиспользуется подходящая механика, но остановленное пользователем исследование opencode-kit не возобновляется и его задачи не закрываются этим change. Наши узкие сравнения относятся только к перечисленным новым tool workflows. Quantitative benefit 5.3/5.4/6.4 остаётся открытым и ждёт отдельного решения пользователя.
- `migrate-harness-to-rust` меняет owning runtime файлы. Будущая реализация сначала проверяет актуальную identity и правит существующего владельца; параллельный Python/Rust интерфейс ради этой спеки не создаётся.

## Risks / Trade-offs

- **Ошибочная graph identity или stale results** -> exact roots/generation/coverage и fresh-source fallback; никаких отрицательных выводов только по графу.
- **Потеря памяти при rename, конфликте или частичной записи** -> owned failure tests, Git diff, сохранение обеих версий, явное незавершённое состояние и проверка ссылок; не предполагать транзакционность Serena.
- **Выдача потеряла существенную ошибку** -> независимые O1 негативные случаи, восстановление деталей; оптимизация отклоняется при потере смысла.
- **Браузерный batch повторяет внешнее действие** -> owned targets, step evidence и продолжение только после проверки эффекта.
- **Optional путь добавил процесс, модель или обслуживание** -> полная стоимость и проверенные limits/lifecycle; при отсутствии выигрыша сохранить baseline.
- **Маршруты стали новым постоянным контекстом** -> короткий skill entry, выборочные references, отсутствие лишних model calls и hooks.

## Migration Plan

1. На реализации сверить текущий source/runtime и владельцев, зафиксировать узкий baseline и существующие конфликты спеки. Не менять рабочую среду ради повторения уже действительных проверок.
2. Доставить краткие маршруты и qualification; проверить C/S/O/B на owned targets. Выполнить M/G/Q оценки и выбрать путь по заранее определённым критериям.
3. Согласовать owning документы и затронутые planning artifacts отдельными scoped правками; связанные незавершённые требования сохраняют честный статус.
4. Применить принятый выбор через существующий installer. Два независимых owned Git roots вне harness, один fresh clone и named child проверяют discovery/use и данные; модели/подписки не перенастраиваются.
5. Упражнить update, перенос kit и disconnect/rollback в isolated lifecycle roots, затем проверить реальную глобальную активацию. Откат возвращает kit-owned маршруты/настройки; проектная память, внешние shared installs и чужие edits сохраняются. Изолированная проверка не называется проверкой отдельного физического ПК.
