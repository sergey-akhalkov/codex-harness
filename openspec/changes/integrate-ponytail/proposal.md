# Proposal

## Why

A normal harness installation on another PC should deliver Ponytail as an active default. Maintaining equivalent principles and workflows in both projects would create conflicting instructions and duplicate maintenance; the harness should consume Ponytail's original package and retain only its additional obligations.

## What Changes

- Include the original Ponytail Codex plugin in ordinary installation and deployment, with an immutable upstream revision, declared runtime prerequisites and the existing update, check, recovery and disconnect lifecycle.
- Enable Ponytail by default after native hook trust is granted. A first-use trust review is an accepted setup step; pending trust, explicit disablement and failed loading remain visible rather than being reported as active.
- Assign each overlapping instruction or workflow to one owner. Remove equivalent harness-authored guidance only after verified upstream coverage; preserve stronger or additional requirements as concise harness supplements.
- Allow Ponytail's required hooks as a specific exception alongside the existing RTK selection. Keep retired diagnostic and Stop handlers disabled and preserve native trust and explicit user choices.
- Preserve normal operation across fresh sessions, resume, compaction and concurrent work, and verify actual consumption outside this checkout before claiming delivery.
- Keep upstream sources, licensing and attribution intact. Upgrade only to an explicitly selected, checked revision; do not fetch an unreviewed moving branch during ordinary startup.

## Capabilities

### New Capabilities

- `ponytail-integration`: Default Ponytail delivery, verified activation, version selection, coexistence and lifecycle acceptance through the installed Codex consumer.

### Modified Capabilities

- `global-working-principles`: Compose upstream-owned guidance with harness-specific supplements, preserve requirement coverage and account for the complete instruction load without a second policy copy.
- `linked-global-kit`: Distinguish first-party live sources from the external plugin package, include Ponytail in ordinary delivery, and reconcile the accepted hook selection with trust, ownership and recovery.

## Impact

Use the original Ponytail mode behavior with documented limitations: resume resets to the default, and concurrent sessions can share mode state. The user selected this scope instead of correcting or forking Ponytail. Persistent plugin disablement remains protected by the harness lifecycle.

The implementation affects the native installation routing and core connection, installation metadata and checks, the portable dependency/plugin declaration, and the applicable source-accounting checks. Instruction consolidation covers the common principles, shared developer guidance, responsibility fragments, owned skills and generated assignment guidance where they duplicate Ponytail. Protected external OpenSpec workflows remain unchanged.

Operational documentation changes belong in the existing installation, global-instructions and project-decisions guides. Ponytail remains third-party code; maintained harness integration and tests remain Rust. The supported delivery target remains Windows with Codex CLI; this does not add support claims for other agents or Ponytail's Claude-specific UI.

Acceptance includes local isolated installation and real outside-project consumption, plus an installation/check/recovery handoff in `docs/installation.md` for the agent on another PC. Preparing or executing a separate Windows machine, VM or account is not a prerequisite for completing this implementation; the receiving agent performs target-machine checks. Documentation does not establish that those checks ran. Planning establishes no runtime compatibility, performance or token-savings claim. Existing deployment-preview behavior and unrelated working-tree edits must be preserved during implementation.
