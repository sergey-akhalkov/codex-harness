## Context

Today one heavy-command account admits exactly one tree: `resource_admission::Lease` takes an exclusive lock on `heavy-command.lock` (the same range as a first-byte exclusive lock), and the admitted tree runs in one containment Job that already enforces per-tree commit memory with `JOB_OBJECT_LIMIT_JOB_MEMORY` (default 8 GiB, 30-minute deadline, bounded queue wait). `heavy_command.rs` documents the lock order "account slot first, shared CPU budget second" and nested-heavy inheritance. After `add-shared-agent-cpu-budget`, CPU is enforced by one account-wide shared Job regardless of how many trees run, so serialization now only costs latency. See proposal.md for motivation. The shared CPU job stays CPU-rate only: it also contains non-heavy agent work and must not receive this memory limit.

## Goals / Non-Goals

**Goals:**
- Bounded concurrent admission per account with mechanical queue semantics and holder diagnostics.
- One kernel-enforced aggregate commit-memory envelope per account covering every admitted tree, without a background owner process.
- Policy/reporting surface for slot count and aggregate memory; legacy policies keep working unchanged; slot count 1 restores today's behavior exactly.
- Preserve per-tree containment, deadline, cancellation, cleanup, nested inheritance, `--account` isolation, exit codes and stdout protocols.

**Non-Goals:**
- No change to the shared CPU budget, its policy or its reporting.
- No per-checkout or per-repository scheduling: the account is the only admission domain.
- No strict FIFO ordering guarantee, priority classes or preemption; the queue stays a bounded-wait polling admission like today.
- No distributed or cross-machine coordination.

## Decisions

1. **Slot-set admission that still shares the legacy lock.** Replace the single exclusive `HeavyCommand` lease with `max_concurrent_trees` slots under the same 20 ms poll and queue-wait loop. Every new admission first takes a shared lock on the existing `heavy-command.lock` in that account directory — the same file and overlapping range the previous build locks exclusively, including its first byte — and holds it until the slot is released. It then takes an exclusive lock on one free `heavy-command.slot-N.lock`. Slot files alone never admit a caller. An old exclusive lock therefore blocks every new admission, and any new admission blocks a later old exclusive lock, so mixed versions serialize instead of adding their allowances. Slot count 1 takes that legacy file exclusively and creates no slot file, restoring today's serialized conflict exactly. Holder descriptions move to per-slot records so releasing one slot cannot clear another holder's diagnostic. Alternative rejected: new slot names without the legacy file. That is the bypass: the old exclusive lock and the new slot locks never meet, so the two builds add their trees and neither joins the other's memory envelope. Alternative rejected: a counting state file with a coordinator — it needs stale-holder repair and more states for no benefit at this bound.
2. **Slot count from policy, default 2.** `budget.json` gains `max_concurrent_trees` (positive integer; 1 = legacy serialization) and `aggregate_memory_limit_bytes`. Defaults: 2 slots; a missing aggregate field equals the effective per-tree memory limit (8 GiB when that limit is also default), so a legacy policy's lone tree keeps the envelope it already configured and a nested per-tree job-memory limit is never above its parent. Missing fields mean defaults; the file is never rewritten by reads. An explicit aggregate below the per-tree limit is refused before admission. Alternative rejected: per-checkout slots — checkout identity is not a kernel resource, path/worktree aliasing makes it unreliable, and it does not bound whole-machine impact; account slots do.
3. **Named account aggregate Job using `JOB_OBJECT_LIMIT_JOB_MEMORY`.** Each admitted caller create-or-opens one named Job (`CodingAgentsHarness.HeavyAggregate.<account-hash>`) and sets only `JOB_OBJECT_LIMIT_JOB_MEMORY` (`JobMemoryLimit` = the aggregate limit). It does not set `JOB_OBJECT_LIMIT_PROCESS_MEMORY`, a CPU rate, kill-on-close or breakaway. The caller holds a handle for the tree lifetime and verifies that readback before starting a payload; a name, flag or limit mismatch fails closed. The object disappears with the last handle, matching the shared CPU owner. Nesting stays outermost first: the unchanged shared CPU job, then this aggregate job, then the existing per-tree containment job. Payload creation uses that order, so the job-wide commit limit covers every admitted tree and one tree's kill-on-close cannot reach a peer. Without a CPU budget the aggregate job is outermost. The per-tree job keeps its own `JOB_OBJECT_LIMIT_JOB_MEMORY`, deadline and kill-on-close. Alternative rejected: `JOB_OBJECT_LIMIT_PROCESS_MEMORY` on the aggregate job — that caps each process separately, so concurrent trees sum past the envelope. Alternative rejected: putting the memory limit on the shared CPU job — that job also contains non-heavy agent work. Alternative rejected: splitting the aggregate into per-tree reservations — either shrinks a lone tree or needs live re-limits.
4. **Admission order preserved.** Order stays: slot admission (legacy shared lock, then a slot) -> shared CPU budget -> aggregate Job create/join -> payload creation (outermost Job first). This keeps the archived CPU-budget deadlock argument: a caller waiting for a slot holds no Job handle and no budget lock, and no path takes the CPU owner before the heavy slot. The aggregate establish lock is the same short create-or-open critical section the CPU owner already uses; it is not a second admission queue.
5. **Diagnostics and reporting.** The waiting caller prints one bounded line ("waiting for a free heavy-command slot; k/N busy; holders ...") from per-slot holder descriptions. When the legacy exclusive lock is the blocker and no new holder record exists, the line says the legacy lock is held instead of inventing a holder. `heavy budget` text and JSON add slot count, aggregate memory, per-tree memory and field sources; `check`-surface heavy reporting is extended only if it already prints heavy budget fields.

## Risks / Trade-offs

- [Two concurrent trees can contend for the same memory envelope and fail allocation where serialization previously waited] -> Documented consequence of concurrency; the failure stays inside the Job, diagnostics name the aggregate limit, and slot count 1 restores waiting behavior.
- [Slot polling is not strictly FIFO; a later caller can grab a freed slot first] -> Same ordering property as today's queue; recorded as a limitation, acceptable at the default bound of 2.
- [Mixed old/new binaries on one machine could admit through different lock files and exceed both the slot bound and the aggregate envelope] -> New admission holds a shared lock on the legacy `heavy-command.lock` for the whole slot lifetime, so it conflicts with the previous build's exclusive lock in both directions. Slot files cannot admit a caller by themselves. Mixed versions serialize; they cannot add their allowances. Moving every heavy caller to one build remains the rollout note, not the enforcement mechanism.
- [Aggregate Job lifetime depends on caller handles] -> Same lifetime model as the shared CPU budget: last handle out closes it; orphan windows only affect reporting, never enforcement, and 4.3-style lifecycle tests cover owner death.

## Migration Plan

Ship behind policy defaults in one release: new fields optional, default slot count 2, missing aggregate memory equal to the effective per-tree limit. Rollback is setting `max_concurrent_trees` to 1 or deploying the previous build. No lock-file rename is required: the previous build still excludes current callers through `heavy-command.lock`, and current callers still exclude it. Admission state remains transient locks and kernel objects.
