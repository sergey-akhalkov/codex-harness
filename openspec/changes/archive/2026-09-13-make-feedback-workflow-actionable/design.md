## Context

See [proposal.md](proposal.md). The current principles and two source-linked skills already require decomposition and valid reuse. Their recorded adoption separates synthetic decisions from one real build/test comparison; it does not establish reliable behavior in every long interactive task. The archived adaptive delta is missing from both affected main specs. Other active work changes native execution and skill refresh; this change preserves those scopes.

## Goals / Non-Goals

The implementation makes an existing behavioral decision easier to select and execute at a failure or consequential repeat. It updates instructions, descriptions and current operation records. It adds no orchestrator, mandatory reflection step, general UI driver, new dependency or universal attempt limit. Consumer-specific driver changes and the unfinished native controller are not prerequisites to editing this pack's instructions.

## Decisions

### Put the decision before the repeat

Consolidate the existing speed/feedback paragraphs around the unresolved fact, discriminating observation and smallest operation preserving the relevant conditions. Expand the verification skill's discovery description to include slow or inconclusive checks. Its feedback section provides the mechanics; the token skill owns prepared-state reuse. This is more actionable than another global warning or a new always-loaded skill and avoids a second owner for the same policy.

Direct exploration means that an agent chooses a bounded tool action from observed state, then observes its effect before deciding the next action. It does not require the user to click, an unattended speculative script, or mastery of an entire interface. Understood actions become reusable through the existing mechanism, followed by required full acceptance. When a short path is missing, first inspect supported step/attach/observe capabilities; a bounded authorized improvement is preferable to repeating the expensive path merely to learn its next prerequisite.

### Keep failure visibility and recovery distinct

The verification skill separates preparation, driver, product, observer and restoration. It directs the agent to available phase/error evidence while cleanup proceeds, and preserves unknown state when that evidence is unavailable. The token skill discourages status-only polling as a substitute for a new fact. Neither instruction authorizes killing an unknown process tree, stealing a session, removing a guard or treating an interrupt as recovery. Changes to an actual consumer's reporting mechanism still require that task's authority.

### Repair current requirements without rewriting history

The two deltas carry the missing archived adaptive requirements; the global delta also adds the new behavior. At synchronization, merge them into the existing main specs, preserve unrelated content and compare every requirement/scenario before moving the change. Historical adoption remains historical. The current operation guide receives only delivery conditions and concise evidence limits, with private inputs and detailed results outside Git.

### Verify the decision through actual effects

Before the behavioral run, select and record a bounded real installed-tool/application task outside this checkout, its owned input, persistent prepared resource or expensive preparation, expected final product result and independent check. Use a fresh ordinary native conversation, the actual linked policy/skill sources and required conversation visibility. The prompt supplies the task and effect limits, not the intended choice to decompose. Preserve the actual difficulties encountered and all attempts; do not manufacture an agent pass from a narrated answer.

Acceptance covers: successive driving/observation difficulties resolved at a smaller boundary; disagreement between action and observation; primary failure distinct from a pending supervisor/recovery; preserved required full integration; a cheap direct task; ended or changed state; and resource ownership. Combine compatible cases in one task and use bounded counterexamples for conditions absent from the real run. Counterexamples do not establish compatibility with an unexercised application. Do not interact with another task's live desktop or service. Inspection and preparation can continue independently until any required shared resource is available.

Capture elapsed time through setup, investigation, correction, checks and recovery, plus full preparation counts and user interventions. The current change claims only exercised decisions and any directly observed removed repeat; it does not rerun the old benchmark or infer universal gains. Loading, behavior, final product effects and recovery each need evidence. Any missing mandatory case keeps implementation and archive open.

## Risks / Trade-offs

- More prose can weaken discovery: replace overlapping paragraphs, keep the skill description discriminating, and avoid a new checklist document.
- Warm state can hide integration defects: check relevant validity and preserve required reset/startup checks.
- An agent can recite the rule without using it: inspect tool calls and independently check the resulting artifact or application state.
- A new source does not prove an old session updated: record current loading separately and preserve the older-session uncertainty.
- Test setup can displace delivery: reuse installed mechanisms and owned inputs, retain failed evidence, and correct the smallest established gap before another dependent run.

## Migration Plan

Preserve the touched source baseline privately, update the canonical owners, validate text/link hygiene and skill format, and verify the existing source links from outside this checkout. No reinstall is necessary when those links are correct. Exercise fresh native behavior with owned resources and independently check the result and recovery. Update the existing operation and decision records, synchronize both deltas, validate their final main-spec content and archive only with all tasks complete. Rollback restores only this change's source edits and uses fresh context; it does not disconnect unrelated capabilities or stop an active consumer.
