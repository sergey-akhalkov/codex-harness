# Proposal

## Why

A normal harness setup on another PC should deliver the original Ponytail plugin by default. Equivalent rules and workflows should have one owner, with the harness retaining its additional obligations.

## What Changes

- Include verified native Ponytail installation and hook review in `docs/installation.md`, as part of ordinary setup.
- Enable the original plugin by default without copied skills or project-local setup.
- Remove genuinely equivalent harness instructions after checking upstream coverage and loading.
- Document the original resume and shared-mode limitations and verify the final composition outside the harness.

## Capabilities

### New Capabilities

- `ponytail-integration`: Native setup, default activation and a usable other-PC handoff.

### Modified Capabilities

- `global-working-principles`: Distinct ownership of Ponytail rules and harness supplements.
- `linked-global-kit`: External native-plugin consumption and the accepted Ponytail hook exception.

## Impact

The user confirmed native installation, default enablement, installation documentation and rule deduplication as the complete scope. The agent-added custom package update, rollback, removal, ownership subsystem and expanded lifecycle test matrix are excluded, not deferred requirements.

Codex remains the package and trust owner. No new harness package manager, transaction journal, recovery protocol or Check subsystem is required. Only a demonstrated conflict in existing hook selection may need a narrow correction.

The receiving agent executes the guide on another Windows PC; no separate machine, VM or account is required here. The selected external project remains read-only. Prepared extra implementation remains preserved outside the delivered change, without acceptance claims.
