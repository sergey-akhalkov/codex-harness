## Why

An instruction to justify complexity can still reward the first plausible mechanism: naming a benefit does not establish that the mechanism is the best way to obtain it. Agents need to interpret the intended outcome, actively seek simpler complete solutions, and challenge costly implementation choices before those choices become code, process and normative obligations.

## What Changes

- Make independent engineering judgment explicit: distinguish goals, binding constraints and proposed means; explain a material weakness and recommend a better supported approach while preserving user authority and existing authorization.
- Require a proportionate search for a simple complete solution before consequential design or implementation. Compare relevant alternatives by clarity, coupling, state, resource use and the full cost of development, verification, operation, recovery and change.
- Preserve agreed behavior, correctness, data integrity, reliability, performance and mandatory acceptance checks. Added complexity may be the appropriate choice when concrete requirements or verified constraints justify it.
- Treat growing exceptions, scattered changes and repeated difficulty understanding ordinary work as reasons to reassess the approach. Keep requirements distinct from replaceable design decisions and retain only useful verified lessons in existing project records.
- Prefer project-native automated tests and reproducible scenarios for requests for proof. Establish a concrete gap before adding special verification infrastructure; distinguish actual observations from agent-authored assertions and preserve necessary diagnostic, product, recovery and audit data.
- Deliver the behavior through the existing global principles and relevant pack-owned records, removing contradictory or duplicate guidance. Verify fresh external loading and actual task behavior without adding a recurring review ritual, scorecard or evidence system.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `global-working-principles`: Independent engineering judgment, deliberate simplicity, comparative justification of complexity, proportionate verification and demonstrated adoption through the existing global instruction lifecycle.

## Impact

The implementation owner is [global/principles-of-work.md](../../../global/principles-of-work.md), with concise decision and operation updates in [project decisions](../../../docs/project-decisions.md) and [global instructions](../../../docs/global-instructions.md). Review the existing pack-owned verification, token-workflow, memory and delegation guidance for actual conflicts; change only conflicting clauses and necessary references rather than copying the philosophy into every file.

The supported delivery remains Windows Codex through the linked global `AGENTS.md`, covering main and delegated work across projects. Externally maintained OpenSpec skills, schemas, templates and workflow configuration remain outside the edit scope. Existing product requirements, permission boundaries and unfinished changes remain authoritative.

This change introduces no executable feature, dependency, new skill, agent, report protocol or blanket prohibition on stored results. It does not clean another repository or publish private examples. Planning artifacts capture the agreed behavior; implementation and its acceptance remain separate work.
