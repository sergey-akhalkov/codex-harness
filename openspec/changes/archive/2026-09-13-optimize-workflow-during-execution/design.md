## Context

See [proposal.md](proposal.md). The current global principles and two installed skills already describe decomposition, observed interactions and valid reuse. The missing emphasis is sustained selection of a useful next action when individually plausible fixes repeatedly revisit one expensive stage. Other active changes already modify verification infrastructure; this change preserves those edits and their acceptance.

## Goals / Non-Goals

Strengthen decisions in the existing owners, replacing overlapping paragraphs rather than adding an always-loaded workflow. Deliver through the existing symbolic links. No runtime controller, generic UI adapter, recurring reflection job, new evidence protocol or changes to a private consumer are needed. This is prompt-level guidance, not a scheduler that can enforce future agent compliance.

## Decisions

### Keep the decision and the mechanics in their current owners

The global speed/feedback section owns the trigger and obligation to act. The verification feedback reference owns distinguishing observations and preservation of the original check. The token workflow reference owns reset/restart/reuse comparisons, proportionate cost measurement and decision-relevant delegation. Short entrypoint routes make these references discoverable. Existing records describe installation and evidence limits without duplicating the detailed procedure.

A new optimization skill would compete with these owners and require another routing decision. A mandatory timer or retry counter would miss differently named failures while burdening short tasks. Instead, reconsider at informative tool results, observed stalls or task transitions; a different error is useful only when it resolves a question or changes the next action.

### Preserve the real feedback conditions

For uncertain interactions, inspect, act, observe and learn the necessary return path before encoding an entire replay. Exercise the actual automation function against valid state, then integrate and finish the required parent run. Compare reset and restart rather than requiring one permanent session. A different diagnostic environment can hide the original condition; held artifacts and unknown restoration are not reusable state. This applies to CLI, build and service work as well as UI automation.

### Invest only where the remaining task can benefit

Use current timing evidence or a small measurement when it can change the choice. Compare saved remaining repeats with preparation, implementation, integration, verification and recovery, counting overlapping wall time once. Do not require a numeric estimate for a plainly cheaper direct action. When authorized delegation is worthwhile, give a worker a specific missing fact needed by the parent while the parent continues independent work; no permanent efficiency monitor is added.

### Reuse official practices under their stated conditions

Reviewed official sources on 2026-09-13:

- [DORA small batches](https://dora.dev/capabilities/working-in-small-batches/): bring feedback close to useful work; this does not prove a measured gain for this pack.
- [Playwright live debugging](https://playwright.dev/docs/debug): reuse an open environment and edit locators while observing their effects. Reuse the approach, not its browser-specific dependency or disabled debug timeout, for other applications.
- [OpenAI skills](https://learn.chatgpt.com/docs/build-skills): keep entrypoints and descriptions focused and use supporting references for conditional details. Verify the actual installed links and fresh prompt separately.

### Acceptance uses existing tools and explicit evidence limits

Preserve the touched working-tree baseline privately. Use existing skill validation, native source/link audit, OpenSpec validation and model-free prompt inspection. Check global links and fresh discovery from an owned external directory; do not infer that an already running session reloaded.

Use one independent visible native task on an owned external OpenSpec project snapshot, with the final installed skills available, realistic inconsistent change artifacts, an existing initial validation failure, unchanged expected requirements and an independent final CLI/content oracle. Supply the requested outcome and allowed effects, not the desired sequence of commands. Observe whether the agent investigates the shared artifact problem and uses focused evidence before final whole-project validation. Include a cheap local documentation correction. Retain tool evidence, resulting files and elapsed time privately; verify the output independently rather than trusting the final answer.

Use a separate bounded continuation of that evaluator for synthetic counterexamples not exercised by the artifact task: an open application with different control failures, ended/changed state, a necessary cold-start check, pending recovery, reset versus restart and worker payback. These establish decision coverage only, not live UI compatibility. No controller or another task's desktop/application is used. A model-backed check requires its existing visibility and authorization conditions; establish those before dispatch rather than building a new evaluation system.

Record observed loading, actions, product checks and limits in the existing global-instruction guide. The external task does not establish a comparative speedup, long-session adoption reliability or close other changes' real-consumer/benchmark obligations. All cases required by this change must be checked before archival.

## Risks / Trade-offs

- More guidance can obscure decisions: replace overlapping text and retain short conditional routes.
- A smaller check can lose the trigger: preserve required state and full acceptance, and include counterexamples.
- A model can repeat the intended answer: inspect actual tool actions and independently validate the external product; label synthetic decisions separately.
- Evaluation can become its own expensive project: use the installed CLI, one owned consumer and existing validation mechanisms; no new maintained executable infrastructure.
- Source links update future reads, not old contexts: explicitly verify fresh input and preserve that operating condition.

## Migration Plan

Save source baselines outside Git, update the canonical owners and existing records, validate and exercise final linked inputs outside the checkout, then synchronize both deltas and archive via the installed CLI. Rollback restores only this change's source differences and starts fresh context; preserve unrelated dirty changes, links, settings and active work.
