## Goals / Non-Goals

**Goals:**

- Сохранить официальный Codex и прямое чтение исходников kit, предоставив MCP и диагностику всем применимым локальным точкам входа.
- Разделить владение установками, регистрациями, проектными данными и жизнью процессов; общий бинарник не означает один изменяемый workspace на все проекты.
- Получить первый сквозной сигнал на существующих установках до обновления общих зависимостей, затем проверить все четырнадцать обязательных языков и доступность YAML/QML/HTML/CSS и сценарии.

**Non-Goals:**

- Форк Codex, собственный агентный runtime, обновление компиляторов/lockfiles целевых проектов и автоматическое исправление найденных ошибок.
- Перенос всех OpenCode plugins и workstation UI. Переносятся необходимые эффекты подключения выбранных инструментов.
- Новая поддержка ОС и облачных удалённых хостов. Это не разрешает вычёркивать язык, backend которого неудобен на Windows: совместимый маршрут нужно реализовать, а невозможность остаётся препятствием завершению.

## Decisions

### 1. Источники и нативные регистрации имеют разное владение

Расширить существующий inventory зависимостями, серверными определениями, языковой матрицей и источником hooks. Для MCP использовать небольшие пользовательские нативные регистрации, содержащие имя и ссылку на repository-owned точку запуска. Она читает определение сервера непосредственно из checkout и разрешённые машинные пути из локального реестра установок. Это допускаемые спекой регистрации путей, а не копирование тел конфигурации.

В базовый пользовательский config добавляются принадлежащие kit регистрации ссылок на точки запуска; существующие значения, формат и чужие MCP сохраняются. Полные команды upstream-серверов, выбор транспорта и повторяемые настройки имеют один источник в kit. Профиль `harness` продолжает владеть своими прежними настройками и не дублирует MCP-регистрации. Использовать только проверенный структурный редактор TOML; совпадение чужого имени — конфликт, а не повод заменить запись.

Фактический CLI/resume probe обнаружил гонку начального каталога: необязательные MCP продолжают запуск после стандартного ожидания 1000 мс, и первые `ALL_TOOLS` не содержат уже зарегистрированных tools. Нативная настройка `mcp_optional_startup_grace_ms=0` устранила сбой в той же сохранённой сессии, включая короткий low-effort turn. Регистрируем этот единственный параметр готовности вместе с путями как машинную политику соединения, с отдельным владением и восстановлением прежнего отсутствия/значения. Это не тело upstream-конфига и не его deployment-копия. Настройка ждёт конечный `startup_timeout_sec`, сохраняя необязательность серверов; `required=true` не используется, чтобы недоступный MCP не запрещал всю сессию. Явное чужое несовместимое значение сохраняется с сообщением о конфликте. Контракт проверен на CLI 0.153.4 и в [официальной configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

Hooks на текущем ПК подключаются прямой ссылкой пользовательского `hooks.json` на repository-owned источник. Если на другом ПК этот путь уже занят, сначала проверить альтернативный нативный слой с прямым чтением источника; при отсутствии такого слоя показать конфликт по существующему lifecycle-контракту, сохранив чужие hooks. Нельзя автоматически слить тела hooks в новый deployment-файл. Одни и те же события не должны регистрироваться одновременно несколькими слоями.

Почему не ограничиться текущим профилем: [файловые профили](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) выбираются через CLI-флаг; он не доказывает загрузку другим клиентом. Почему не обычная установка plugin: [локальные plugins](https://developers.openai.com/plugins/build/plugins) обычно копируются в cache, что не удовлетворяет принятому прямому потреблению. Plugin нужен только если проверенный механизм прямой ссылки решит конкретный конфликт регистрации; создавать его заранее не требуется.

Первый runtime probe проверяет маленькую MCP-регистрацию-путь, загрузку hooks из ссылки и чтение изменённого исходника через native CLI и unprofiled app-server/установленный desktop. Если конкретная версия не соблюдает эти контракты, глобальная активация остаётся незавершённой; копирующий fallback или незаметное сужение до launcher-сессий исключены.

### 2. Зависимости обновляются одной явной операцией

Добавить update-операцию к существующему `install.ps1`, сохранив его прежние режимы и preview. Install сначала строит план reuse/install/update; Check сообщает фактическое состояние. Проверка версий использует официальные package/release metadata, а не запуск `npx -y` или `uvx` при каждой сессии.

Локальный реестр содержит package identity, manager, executable path, selected version, источник, дату проверки, владельца и состояние обновления. Секреты туда не входят. Установщик не доверяет одному PATH: на машине два разных Graphify-пакета с одинаковыми командами. Выбирается `graphifyy` с проверкой Python module identity; npm `@dreamtree-org/graphify` сохраняется как посторонняя установка.

По умолчанию владелец связей и зависимостей — один `UserHome`. Явный `DependencyUserHome` позволяет подключить отдельный consumer home к уже проверенным общим установкам без изменения чужих skill links/PATH. Он сохраняется в installation/pending metadata; несовпадение владельца отклоняется до эффектов, блокировки обоих владельцев берутся в постоянном порядке. Никакого неявного fallback на зависимости текущего аккаунта нет.

Перед заменой: проверить активных потребителей, получить восстанавливаемый пакет/версию и необходимые снимки изменяемых данных, подготовить обновление, проверить протокол и операции. После замены: проверить Codex и OpenCode, затем зафиксировать выбранную версию. Версионные LSP-каталоги Serena можно временно использовать для испытания/отката; это не отдельная постоянная поставка для Codex. Не удалять старый каталог, пока известные потребители ссылаются на него. Закреплённый uv receipt и workstation identity должны соответствовать итоговому состоянию; их нельзя обходить произвольной переустановкой.

Не ставить все необязательные runtime автоматически при старте: четырнадцать обязательных языков и доступность YAML/QML/HTML/CSS подключаются глобально, а отсутствующие зависимости разрешаются через явную операцию подключения языка/install/update. Все принятые строки матрицы всё равно требуют реализации и проверки до завершения change. В новом окружении установщик перечисляет требуемые SDK и предоставляет объявленный путь их подключения.

### 3. Четыре upstream MCP сохраняются, адаптер добавляется для конкретного пробела

Serena запускается из существующей установки с [контекстом Codex](https://oraios.github.io/serena/02-usage/030_clients.html#codex-cli-and-app). Workspace определяется по фактическому проекту сессии; app `cwd` нельзя без проверки принимать за корень проекта. Codebase Memory использует существующий frontend/shared backend и проектную идентичность. Nuphus сохраняет существующую установку и применимые параметры взаимодействия; при проверке используются собственные disposable desktop/browser targets.

Для Graphify диспетчер проверяет identity и доступность существующего endpoint, получает авторизацию через разрешённый локальный механизм и сохраняет явный `repo` для PR-операций. При недоступности общего сервиса можно поднять session-local stdio через тот же Python и существующий graph. Минимальный transport adapter оправдан только там, где нативная регистрация-путь должна соединить STDIO клиента с существующим HTTP сервером. Нельзя подменить общий knowledge graph случайным графом cwd или переносить секрет в исходник.

В Serena 1.7.0 есть `get_diagnostics_for_file`, но нет готовой операции «сопоставить все изменения данного tool call и вернуть hook-результат». Более того, `serena/tools/tools_base.py` явно содержит `ENABLE_DIAGNOSTICS=False`; стандартный Codex patch не является правкой Serena.

Поэтому добавить небольшой repository-owned MCP-адаптер `harness-lsp` для автоматической диагностики и операций языков, которых не хватает основному MCP. Пятый технический endpoint не заменяет ни один из четырёх запрошенных MCP. Он использует существующие LSP executables и готовый клиентский слой там, где тот пригоден; предпочтительный первый backend — установленный Serena/solidlsp с проверенной версией. Вызовы его Python API изолируются в одном адаптере и проверяются при update. Поддерживаемый LSP-клиент нужен только для оставшихся конкретных backend, а не как новая универсальная платформа.

Каждый процесс Codex владеет своим adapter connection; внутри него LSP запускается лениво по canonical root + language + settings identity и переиспользуется между правками. Совместное использование бинарников сохраняется и при отдельных процессах Serena/diagnostics/OpenCode. Нельзя подключиться к чужому stdio-процессу или менять его workspace. Дублирующую нагрузку измерить на реальных проектах; объединять процессы только если это сохраняет изоляцию и сокращает измеренные затраты.

### 4. Один hook-вызов сопоставляет изменения и возвращает диагностику

Использовать синхронный `PostToolUse` для patch, Bash и MCP-вызовов. Нативный handler `type: mcp_tool` адресует уже подключённый MCP; `input` поддерживает поля события. Возврат `hookSpecificOutput.additionalContext` доставляет результат модели. Обычный stdout этого не обеспечивает. MCP hook не запускает отсутствующий сервер и не вызывает рекурсивные hooks. Точный trust и формат ответа проверить на установленном consumer. [Контракт hooks](https://learn.chatgpt.com/docs/hooks#mcp-tool-hooks)

Предлагаемая операция адаптера — `diagnostics_after_tool`: вход содержит workspace, session/turn/tool-use identity и исходный tool input/result. Внутри одного вызова она читает журнал изменений, согласует версии файлов, получает диагностику и формирует model-visible summary. На последовательный обмен результатами между независимыми hooks полагаться нельзя.

Основной формат результата: canonical root, относительный путь, content generation, backend, status, diagnostics, omitted count и ссылка на полный локальный отчёт. Начальный предел ожидания — 30 секунд на batch, включая адаптер; таймаут клиента не должен быть короче этого без явного изменения бюджета. Ошибки диагностики не заменяют успешный результат исходного edit и не запускают autofix.

### 5. Источник истины — фактическое содержимое файлов

До первой потенциально пишущей операции синхронный command hook `PreToolUse` создаёт независимый локальный baseline и запись invocation, не ожидая MCP handshake. На повторных вызовах он фиксирует границу уже существующего journal. Это небольшой bootstrap/учёт изменений, не установка пакетов и не запуск анализа на каждую read-only операцию. Адаптер после подключения принимает сохранённое состояние, а не объявляет уже изменённый workspace исходным. Если baseline не удалось получить, сохраняется явный unknown/pending статус: позднее подключение не может превратить пропущенную первую правку в clean.

Адаптер продолжает журналировать фактические изменения. События файловой системы используются как ускорение, а не единственный источник истины. На границе завершённого tool call выполняется сверка метаданных и content hashes для затронутых кандидатов; при overflow/lost events — восстановительная сверка поддерживаемых исходников. Baseline включает untracked и pre-dirty files. Пути из patch/MCP arguments помогают сузить работу; shell-текст и Git diff недостаточны для полного обнаружения.

Registry roots учитывает worktrees, вложенные проекты, symlinks и явно разрешённые additional roots. Generated/vendor/cache directories исключаются по объявленной политике проекта, но уже открытый редактируемый исходник нельзя пропустить только из-за `.gitignore`. Watcher не должен сам произвольно расширять доступ за допустимые roots. Изменения конфигурации языка инвалидируют соответствующий analysis state.

LSP синхронизация обновляет документ до анализируемой версии. Для push и pull backends адаптер определяет, когда результат относится к актуальному содержимому; пустой актуальный diagnostics array означает очищенную ошибку, отсутствие notification — нет. При backend без надёжного маркера свежести нужно доказать применимый synchronization contract; сомнительный результат обозначается pending/stale, не clean.

Поздняя запись background command и pending analysis попадают в последующую сверку. `Stop` и `SubagentStop` используют тот же dirty journal для завершающей проверки; запись сопоставляется с root, фактическими child/agent, turn и tool-use идентификаторами. Один parent session_id недостаточен. Подагент не должен возвращать результат родителю с незаметно потерянной pending диагностикой. Новый цикл допускается только при новых неразобранных результатах и имеет конечный предел. Не вводить бесконечный stop-loop из-за существующей ошибки/неработающего сервера. При недоступном MCP отдельный ограниченный command handler читает сохранённый journal и доставляет явный unresolved результат; он не полагается на вызов отсутствующего MCP. Результат failure/unavailable остаётся видимым при завершении; нельзя заявлять «проверено без ошибок».

### 6. Матрица языков является критерием приёмки

Пользователь уточнил объём: только Rust, TypeScript, JavaScript, PowerShell, Python, Delphi, C++, C#, JSON, Markdown, TOML, XML, CMake и Bash; YAML, QML, HTML и CSS подключаются при наличии готовой совместимой поддержки. Остальные языки, включая F#, не входят в change. Единственная нормативная матрица — [global-code-tools/spec.md](specs/global-code-tools/spec.md). В реализации разворачивается машиночитаемая матрица с выбранным backend, официальным источником, runtime, project inputs, операциями и доказательствами. Альтернативные backend одного языка не требуют повторных установок ради количества. Не поддерживаемые Serena строки получают совместимый маршрут в адаптере.

Начальный вертикальный срез проходит TS/JS, затем остальные выбранные языки. Это порядок получения обратной связи, а не отдельный уменьшенный объём. Для Delphi использовать реальный проект с unit/include paths и зафиксированным диалектом, а также маленький reproducible пример введения/исправления ошибки. Нельзя преобразовать Delphi исходник в Free Pascal и назвать это поддержкой Delphi. Если нужен пользовательский SDK/реальный проект, сначала обнаружить уже доступные конфигурации; запросить только недостающий доступ или выбор конкретного проекта.

### 7. Проверки разделяют протокол, интеграцию и глобальную поставку

Расширить существующие standalone PowerShell-проверки вместо введения общего package runner. Сначала фактическая версия/help/schema и один сквозной consumer probe, затем проверки значимых failure paths. Model-backed проверки остаются явно запускаемыми opt-in скриптами; для реализации этой принятой спеки они обязательны и входят в согласованный объём проверки.

| Проверка | Свидетельство успеха |
| --- | --- |
| Native integration | Нативная регистрация-путь и связанный hook реально читаются; исправление исходника влияет на новый consumer; hook summary виден в контексте агента |
| MCP | Реальные handshake и meaningful tool call всех четырёх MCP; mutation проверяется на disposable target |
| LSP | Для каждой строки матрицы actual server navigation/diagnostics согласно обещанным операциям; Rust, TS/JS, PowerShell, Delphi имеют ошибку и её очистку |
| Edit routes | Native patch, shell, MCP; partial failure, yielded command, rename/delete/create, pre-dirty/untracked files |
| Freshness/isolation | Быстрое исправление до старого ответа, dependent errors, два разных проекта/worktree, одновременные subagents |
| Lifecycle | Reuse, актуализация, несовместимая версия, rollback, conflict, moved checkout, disconnect, сохранность OpenCode |
| Global delivery | Новые обычные CLI-сессии и применимые установленные local desktop/IDE consumers вне checkout, без project-local registration |
| New host | Чистая VM/Windows account или явно описанное изолированное окружение; отсутствующие зависимости поставляются по декларации |

Для concurrency и malformed protocol полезны детерминированные doubles, но ими не подменять реальный LSP и model-visible automatic path. Исходные тесты installer/launcher запускаются при изменении их областей; Windows TUI — при изменении точки входа или настройки/trust. Итоговый отчёт связывает требования со сценариями и фактическими результатами.

## Risks / Trade-offs

- **P1: обновление ломает общий инструмент или данные OpenCode** → проверить активных потребителей и ownership/identity, сохранить восстановление, проверить оба клиента; не завершать update при недоказанной совместимости.
- **P1: диагностика другого проекта или старой версии приводит к неверной правке** → canonical roots, generations, invocation identity и явные stale/unavailable состояния; отдельные concurrent проверки.
- **P1: shell writes пропущены и агент получает ложный clean** → journal + content reconciliation, untracked/pre-dirty/partial-failure проверки; не считать отсутствие события анализом.
- **P1: команда/секрет попадает в shell или журнал как исполняемый текст** → структурные аргументы процессов, данные событий как JSON, редактирование конфигурации без string-built shell, скрытые окна фоновых helpers и исключение credentials из отчётов.
- **Новая версия языка требует недоступную ОС/SDK** → явная незакрытая строка с точной причиной; совместимый backend или отдельное решение пользователя, без автоматического удаления требования.
- **Native hook trust или запуск MCP ещё не готов** → отличать configured от active; проверить доверие exact definition и доставку ошибки отсутствующего adapter; пользовательские проверки доверия не обходить записью внутренних hash.
- **Повторный запуск LSP и сканирование увеличивают задержку** → ленивые долгоживущие процессы, изменённые content generations, отсутствие full analysis на read-only операции; измерить cold/warm latency и исправить обнаруженный bottleneck.
- **Зависимость от solidlsp API и расхождение опубликованной схемы с CLI** → узкий адаптер, запись проверенных версий и ранний реальный probe; схема main сама по себе не является доказательством релизного поведения.

## Migration Plan

1. Снять read-only inventory, сохранить исходные версии/ownership и выполнить preview. На текущих версиях доказать native registrations, hook delivery и один язык в изолированном окружении.
2. Добавить reusable источники, диспетчеры и недостающую диагностику; проверить lifecycle и язык за языком заполнить матрицу.
3. Испытать стабильные обновления, обновить общие установки в безопасном состоянии и проверить существующий OpenCode. Сохранить подтверждённые зависимости и recovery evidence.
4. Глобально зарегистрировать ссылки, завершить необходимые native trust действия и проверить реальные consumers вне checkout. После изменения definitions запускать новую сессию.
5. Проверить чистый host, moved checkout, повторную установку, disconnect и recovery. На текущем ПК оставить рабочую глобальную активацию, удалив test-only registrations.
6. Обновить installation/docs/support matrix и acceptance report. Закрыть задачи только по фактическим проверкам. Архивация не входит в текущий запрос на создание спеки.

При rollback восстанавливаются kit-owned registrations и версии, которые меняла конкретная операция. Уже существующие tools, данные и чужие процессы не удаляются. Невосстановленная часть явно перечисляется в локальном журнале и отчёте.
