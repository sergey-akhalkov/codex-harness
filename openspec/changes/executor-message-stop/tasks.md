## 4. Executor message

- [x] 4.1 Implement `codex-harness executor message --source CHECKOUT --codex-home DIRECTORY --slot N --owner ID [--session ID] (--text TEXT | --file FILE)` in `crates/codex-harness/src/executor_cli.rs`: literal UTF-8 multiline content without shell evaluation, identity verification against the live run, delivery through the recorded endpoint on the same thread, honest queued/delivered/error classification, retry identity so an indeterminate retry cannot silently double-deliver, and explicit completed/stopped/unsupported results naming the exact-session resume remedy. Fold the legacy `executor steer` path into this addressing or retire it without leaving a parallel command; update `USAGE`. Verify with fixture tests for text/file parity, stale identity, finished run, dedup and classification.
  - Implementation lives in the new `crates/codex-harness/src/executor_message.rs` (a `#[path]` module of `executor_cli.rs`, like `executor_stop.rs`), with only the `message` router arm, the `USAGE` entry for it and the removed `steer` arm/function/usage line in `executor_cli.rs`. The legacy `executor steer` subcommand was retired rather than re-pointed: its hand-supplied task-control `--state` addressing cannot name a pooled run, so keeping it would leave a second delivery command that reports "delivered" from a payload it wrote itself. `executor_control.rs` gained the typed `Conversation::request`/`Reply` (a server refusal distinguished from a request that was never answered, with `call` unchanged on top of it) and renders thread `userMessage` items as one `input:` line per item id, so the run's own surface shows a delivered lead input once.
  - Addressing and identity: the command resolves the receipt from `--source/--codex-home/--slot/--owner` (an optional `--session` must equal the receipt's recorded session), then verifies the slot record, the receipt's slot binding, the live lease against the receipt's recorded host identity (a disagreement refuses with nothing sent), the recorded host and app-server child by their exact process identities, the control endpoint record (`endpoint-<index>.json`, thread id required) and the live conversation itself - its session id is the recorded one, its `cwd` is the addressed slot and it reports the receipt's resolved model/provider/reasoning effort. A completed, stopped, partial-stop, failed, defect or interrupted run reports its actual state, cause and result with the exact-session `executor resume` remedy and exit 2; a surface with no control route, no recorded endpoint, no thread, an unverified host/child or a legacy receipt is reported as unavailable with the same remedy and exit 2; invalid options and identity mismatches are refused on the error exit before anything reaches the endpoint.
  - Delivery and classification: an active turn is steered (`turn/steer` with `expectedTurnId`, the nearest supported point of a running tool call, never an interrupt) and an idle thread receives `turn/start` on its own thread - never a new conversation, hidden stop/resume, routing change or task re-send. `delivered` requires the conversation's own items to show a `userMessage` carrying the recorded `clientUserMessageId` (or the exact text) within the bounded evidence window; `queued` is the acceptance answer without that evidence; `error` is the native endpoint's own refusal; an unanswered or untrustworthy answer is `indeterminate`. A rejection is re-read and re-submitted while the addressed slot's turn changes (bounded to 3 rounds) only after a confirmation read found no evidence.
  - Repeat safety: every attempt is recorded in the receipt's `messages` array (the field the stop path marks undelivered) with its content identity (the digest of thread id plus the exact text - the text itself is never copied), the method, the expected and answered turn, the attempt count and the evidence. A delivered or queued content is reported instead of sent again (a queued record is upgraded to delivered when the conversation's own items later show it), an indeterminate or pending attempt refuses the repeat and names the next action, and only a definite error may be sent again.
  - Verified by `cargo test --locked -p codex-harness --test executor_message` (12 checks: literal text and UTF-8 file delivery verbatim to the recorded thread with no `thread/start`, `turn/steer` of the active turn with `expectedTurnId` and no interrupt/new turn, the queued classification, the delivered input rendered once on the run's surface through the real `executor run --file` host and a canned endpoint, stale owner and session refusals that reach no endpoint, completed/stopped/interrupted and unsupported-surface results with the remedy, native-refusal classification with a retry that delivers and an error record that stays retryable, an indeterminate attempt whose repeat never reaches the endpoint, a queued message upgraded by evidence instead of being re-sent, and a queued message marked undelivered by the real `executor stop`), by `cargo test --locked -p codex-harness --test executor_control --test executor_stop` (23 + 6 checks, unchanged behavior on top of the refactored typed request) and by `cargo test --locked -p codex-harness --bin codex-harness` (`the_legacy_steer_subcommand_is_retired` plus the existing executor unit checks). The canned app-server endpoint the control and message suites share now lives in `crates/codex-harness/tests/fixtures/control_endpoint.rs` with per-method answer sequences. Exit codes and the exact behavior are documented in the `executor message` `USAGE` paragraph.
  - Residual outside this slice: `crates/codex-harness/src/main.rs` still lists the retired `executor steer --thread ... --out FILE` line in the top-level help summary (its owner also already omits `watch`, `stop`, `resume` and `run`); the `executor --help` usage of `executor_cli.rs` is the authoritative surface and names `executor message`. Live acceptance against the installed CLI (real dispatch, real steer/queue notification shapes) remains task 6.1; the protocol shapes used here are the installed 0.156.1 CLI's own generated JSON schema (`turn/steer` with `expectedTurnId` and `clientUserMessageId`, `turn/start`, the `userMessage` item with `content` and `clientId`) plus the change's verified baseline, and an unobserved input is reported as queued rather than as delivered.
