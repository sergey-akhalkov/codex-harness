# Design

## Context

See [proposal.md](proposal.md) for the outcome and scope. The existing executor implementation already owns most non-conversation mechanics:

| Existing owner | Reuse |
| --- | --- |
| `crates/codex-harness/src/executor_cli.rs` | Dispatch preparation, assignment/profile validation, pool acquisition and launch binding; separate these from terminal creation |
| `crates/codex-harness/src/executor_control.rs` | Native app-server requests, thread configuration, identity checks, current result/stop/recovery records |
| `crates/harness-core/src/task_worktree.rs` | One repository-wide pool, leases, committed base, preservation and safe reuse |
| Profile resolution and orchestration configuration | Allowed profiles, complete effective configuration, independent executor and pool limits |
| Existing MCP and installation modules | Reuse compatible protocol, registration and lifecycle pieces after checking their server/client roles; their existence does not establish a ready executor MCP server |

Installed Codex 0.164.0 provides native app-server threads, turns, queues, events and client attachment. Its native /agents interface is distinct from the built-in child-agent surface. The current built-in spawn schema has no worktree, provider or profile argument; hooks cannot make unsupported arguments acquire those semantics. Experimental environment features are not a verified replacement.

### Evidence and its limits

Protocol experiments used isolated configuration and synthetic committed worktrees. They changed no global configuration. Raw evidence and process identities remain local; this table records the reusable conclusions.

| Observation | Design consequence / unverified boundary |
| --- | --- |
| One native server admitted two threads in distinct worktrees with the selected external provider/model/effort; the base configuration remained unchanged | Per-thread configuration is a viable foundation. Admission does not prove actual provider/tool execution, full profile consumption or UI visibility |
| Passing a legacy profile name in thread config was rejected; the app-server command also rejected the runtime-only profile flag | Resolve the native profile through the existing owner and pass supported effective overrides; do not forward a profile name blindly |
| A raw effective-config JSON round trip failed on null values; a normalized overlay admitted the threads | Reuse native/source configuration semantics. Do not turn probe-specific null removal into a general configuration serializer |
| Native queue operations worked and one queue submission started a turn automatically | Queue submission has model effects. Avoid a second turn-start; provider request count and usage were not measured and must not be described as zero |
| Threads with no first-turn rollout were loaded but not durable after server shutdown | A returned thread ID is not proof of recovery. Startup failures must preserve the lease and report unavailable history |
| An ordinary daemon started with a short isolated configuration path; elevated daemon startup explicitly refused privileged sharing | A shared ordinary daemon cannot satisfy privilege inheritance for an administrator CLI |
| An elevated standalone stdio app-server initialized and admitted correctly configured threads | Native elevated runtime creation is possible. Protected attachment of the CLI and MCP, actual elevated tool execution and ordinary-client isolation still require proof |
| The controlled process job and an overlong local socket path caused separate probe failures | Do not misdiagnose these fixture constraints as the user's elevation problem; use supported process ownership and endpoint limits |
| Owned probe processes were reconciled and stopped | This establishes restoration of the probe, not production lifecycle acceptance |

### Task 1.1 installed contract

Observed on 2026-10-23 with installed `codex-cli 0.164.0`:

| Contract | Installed evidence and boundary |
| --- | --- |
| Plugin manifest | `.agents/plugins/executors/.codex-plugin/plugin.json` declares plugin `executors`, version `0.1.0`, and `"mcpServers": "./.mcp.json"`. The package is portable: no absolute path, credential or session identity is tracked. |
| MCP configuration | `.agents/plugins/executors/.mcp.json` declares `executors` as a stdio server with `command: "codex-harness"` and `args: ["mcp", "executors"]`. PATH resolution is part of the installed contract. |
| Marketplace | The repository marketplace names plugin `executors` from `./.agents/plugins/executors`. Codex resolves a local plugin source relative to the marketplace root, not the `.agents/plugins` directory; the observed install output is `executors@coding-agents-harness`, enabled, with the expected stdio transport. |
| Caller identity | Codex injects the calling thread as request `params._meta.threadId`. The server accepts only a bounded registry key from that metadata; tool arguments cannot supply or override a lead, run, thread or endpoint. A request without metadata fails before endpoint lookup or pool effects. |
| Endpoint attachment | The server resolves `$CODEX_HOME/harness/lead-endpoints/<threadId>.json`, requires the recorded `threadId` to equal the metadata identity, verifies the recorded app-server process identity is live, connects to that exact loopback endpoint, and requires `thread/read` to report the same thread as `idle` or `active`. A missing or unusable record is an explicit unsupported error with the `codex-harness lead start` remedy; there is no fallback server. |
| Runtime identity | `thread/list` is discovery only: a shared thread store can list an executor thread as `notLoaded` without that thread being active in the lead's runtime. The accepted proof therefore requires `thread/read` on the resolved endpoint and requires the created executor thread to report `idle`/`active` there. The existing CLI spawn path remains a separate app-server and is not evidence of same-runtime attachment. |
| Same-runtime dispatch | The tool calls `thread/start` on the resolved endpoint with the allocated consumer pool slot as `cwd`, `allowProviderModelFallback: false`, the configured default executor profile, the resolved executor role and profile overrides, and `agents.enabled: false`. It verifies the returned identity, routing, title and loaded `thread/read` record before submitting the brief with `turn/start`. After turn acceptance it clears the startup reservation while keeping the slot occupied, so explicit release does not depend on the MCP helper process lifetime. |
| Source and repository | The installed kit source comes from `executor_input::source(None, $CODEX_HOME)`, which reads `settings.sourceRoot` from the installation record. The target repository comes from the calling thread's `cwd` Git root. The kit supplies `global/orchestration.toml`, the configured default profile and pool size; the consumer supplies the pool, worktree siblings, slot records and receipts. A consumer without `global/orchestration.toml` is valid. |
| Owner | `owner` is optional. When omitted, the tool generates `mcp-<caller suffix>-<nanosecond timestamp>`; an explicit owner keeps the collision refusal. No thread, run or endpoint identifier is accepted as authority. |
| Pool and receipt | Slot allocation, assignment validation, base synchronization and profile checks reuse the existing executor dispatch owner. A successful tool result reports run, source, repository, pool size, executor thread, title, slot, consumer checkout, committed base and effective profile; the consumer pool state retains `mcp-<slot>.json` with the same identity. This receipt is separate from the terminal/relay spawn receipt. |
| Refusal | Missing/forged metadata, a mismatched endpoint record, a dead app-server identity and forged tool arguments are refused before a slot claim, thread creation or turn. The forged-argument check rejects unknown fields such as `leadThreadId` or `run`; the exact request returns `isError` with no new receipt or thread. |
| Install and removal | In an isolated Codex home, `codex plugin add executors@coding-agents-harness --json` installed and enabled the plugin, `codex plugin list --json` reported it enabled, and `codex mcp list --json` reported the expected stdio transport. Removal left an unrelated MCP server and settings intact; reinstall preserved it as well. |

The real MCP call used a fresh Codex thread on the existing harness-hosted app-server because the already-running original lead thread had no thread-scoped plugin configuration. That probe thread was a real native conversation on the same endpoint; Codex injected its `_meta.threadId`, the tool resolved that thread's registered endpoint, and the created executor thread and first turn were observed loaded on that same server. This proves the trusted call channel, endpoint attachment and same-runtime thread creation. It does not prove that plugin configuration can be added to an already-started thread without a fresh session; a fresh lead session with the plugin installed before startup remains the ordinary delivery path.

The consumer proof used a synthetic Git checkout without `global/orchestration.toml`, a private isolated home whose synthetic `harness/installation.json` named the kit source, and the same lead app-server. The call omitted `owner`; the generated run label used the caller suffix and a nanosecond timestamp. The tool resolved the kit source and the consumer repository separately, created `consumer-wt1` next to the consumer, wrote `mcp-1.json` under the isolated home's consumer pool state, and reported pool size `6` from the kit configuration. The executor thread ran in `consumer-wt1`, and its first turn executed `git rev-parse HEAD` with the consumer commit and confirmed `global/orchestration.toml` absent.

The first executor turn ran the real brief in the pooled checkout through the configured default profile (currently DeepSeek) and executed `git rev-parse HEAD`, returning the assigned base. The executor thread record reported the pooled `cwd`, title, `deepseek-flash`, `deepseek` and `max`. The `allowProviderModelFallback: false` request field was sent but was not echoed by the thread record, so it is request verification, not an observed runtime assertion. The executor inherited the app-server's sandbox; this slice does not independently prove per-profile sandbox differentiation. The synthetic consumer executor created an untracked `.serena/` tooling directory; the isolated proof lane was preserved as not clean, with no tracked change. The terminal-side watch/pool session display still reads the legacy spawn receipt, so `mcp-<slot>.json` is authoritative for this MCP run until the compatibility paths are reconciled.

### Task 4.1 plugin lifecycle contract

Observed on 2026-10-23 with installed `codex-cli 0.164.0` in isolated Codex
homes:

| Lifecycle | Verified behavior |
| --- | --- |
| Install and update | Core Install/Update runs the native `codex plugin marketplace add <source> --json` and `codex plugin add executors@coding-agents-harness --json` commands with the selected `CODEX_HOME`. The second install/update is idempotent. No interactive install prompt appeared. The plugin is enabled and `codex mcp list --json` reports `codex-harness mcp executors` over stdio. |
| Check | Core Check adds `plugin` to its receipt. `status = "ready"` requires native plugin listing to report the owned source installed and enabled, plus the enabled stdio MCP entry. `installed`, `enabled`, `available`, `changed`, `recorded` and `model_calls` remain distinct. |
| Receipt and recovery | The lifecycle writes `CODEX_HOME/harness/executors-plugin.json` before native effects. A pending receipt records only plugin/marketplace identity, source, resolved upstream command and intended connect/disconnect state. `recover --core-only` replays a pending connect, or a pending disconnect after core removal is committed, and verifies the resulting native state. A pending disconnect while core is still connected asks for the core disconnect to be rerun. No credential or task payload enters the receipt. |
| Disconnect | Disconnect journals its intent before core removal, then removes only `executors@coding-agents-harness`. The shared `coding-agents-harness` marketplace is retained because Ponytail and unrelated plugins may use it. |
| Preservation | The isolated acceptance retained Ponytail and another plugin selection, an unrelated MCP server, model/settings and authentication bytes, a marketplace entry, and synthetic executor-pool dispatch, endpoint and assignment files across install, update, check, recovery and disconnect. Command output did not expose sentinels from those records. |
| Server identity | A spawned installed `codex-harness mcp executors` completed MCP initialize as server `executors` and listed `executor_dispatch`. This verifies the installed stdio command and tool surface, not a model turn or `/agents` interaction. |
| Version and PATH | `.mcp.json` names `codex-harness` rather than a tracked absolute path, so a fresh Codex process must resolve it through the selected PATH scope. Sources without the marketplace declaration report `not-packaged`; a Codex CLI without the native plugin command reports `unsupported` and is not claimed as plugin-capable. The accepted plugin lifecycle host is 0.164.0; the older core baseline does not establish this support. |
| Relocation limit | Codex refuses to add the same marketplace name from a different checkout. The lifecycle fails closed before plugin changes and preserves the existing marketplace, rather than removing state that Ponytail or unrelated plugins may share. A moved connected installation therefore needs an explicit native marketplace decision. |

The acceptance is
`cargo test --locked -p codex-harness --test plugin_lifecycle -- --ignored --exact install_update_check_recover_and_disconnect_preserve_unrelated_state --test-threads=1`
with `HARNESS_PLUGIN_CODEX_EXE` naming the native Codex executable. It builds an
isolated kit source and homes, runs the real lifecycle, starts the installed MCP

The dispatch-only slice did **not** establish automatic delivery while the lead is active or idle, bidirectional question/reply handling, isolated stop/continuation, elevated attachment, two-profile concurrency or native `/agents` UI interaction. Bidirectional delivery is added by the following status/exchange slice; the other conditions remain tasks 1.2-1.5 and must pass before broad migration. These are explicit feasibility conditions, not accepted shortcuts or deferred user choices.

### Executor MCP status and exchange slice

The same `mcp-<slot>.json` receipt now carries a `lease` object with the slot, owner, checkout and exact app-server process identity. Every operation accepts authority only from Codex's `_meta.threadId`: it scans the bounded MCP receipt set, requires the caller to be the recorded lead or executor, requires the canonical pool receipt and an occupied slot with the same owner and checkout, and requires the registered lead endpoint's live process to equal the lease. Tool arguments cannot supply a thread, endpoint or recipient; a lead's `run` argument is only a selection handle resolved among its own verified runs. A lead may also use a recorded `requestId` as a correlation reference; with neither, it addresses its sole recorded run. An executor can address only its originating lead and cannot dispatch descendants.

The server exports six conversational and lifecycle tools:

| Tool | Contract |
| --- | --- |
| `executor_status` | Reads the verified caller's matching runs with exact native thread status and bounded pending-request records (8 runs, 16 requests per run). No matching run is an explicit empty result; an unavailable endpoint or transport read is an error, not an empty run. |
| `executor_message` | Sends one literal message. A lead addresses its sole run, an exact `run` id returned by `executor_status`, or a recorded `requestId`; supplying both requires them to resolve to the same run. Executor-to-lead is a notification with no reply hold. A supplied `clientMessageId` makes the same payload repeat idempotent; distinct ids make intentionally identical text distinct operations. |
| `executor_reply` | Answers one recorded `reply-request` by id. It verifies the caller is that run's originating lead and delivers to the exact executor thread. Only observed delivery resolves the request; queued, refused or indeterminate replies do not. |
| `executor_ask_lead` | Executor-only. It records a stable `lead-<24 hex>` request id in `leadMessages` before attempting delivery, sends a native request to the originating lead, and returns without waiting for the answer. A supplied `clientMessageId` distinguishes otherwise identical question text; when omitted, the id is derived from run and text, so an identical repeat is a retry of the same request rather than a new operation. A temporarily unavailable lead endpoint records an error under that same id; repeating it after recovery sends the same request rather than creating a new one. |
| `executor_stop` | Lead-only. Resolves one verified owned run, adopts its exact executor thread on the recorded shared app-server, requests `turn/interrupt` for the actual active turn, and terminates only that thread's native background terminals. Returns the observed thread state, containment evidence and preserved slot/lease; partial containment is an explicit non-success result. |
| `executor_resume` | Lead-only explicit continuation. `exact` starts one turn on the same recorded thread from the preserved assignment and bounded progress without replaying the assignment; `fresh` creates one new bound thread on the same shared app-server from the preserved assignment, retains the predecessor and records it. No stopped run is resumed implicitly. |

Delivery reuses the existing `executor_message` owner. It attaches to the exact `threadId`, verifies checkout and profile, uses `turn/steer` with the active `expectedTurnId` or `turn/start` for an idle thread, carries `clientUserMessageId`, and observes the recipient's own items for `delivered`. A native acceptance without that evidence is `queued`; an error answer is `error`; a lost answer is `indeterminate`. A rejected steer may be re-read and retried within the existing three-round bound; an unanswered submission is never retried. The attempt is recorded before the request, and a later call with the same identity reconciles or reports the recorded state without resending it. Notifications do not hold completion, and no MCP call waits for the recipient's reply.

For a lead, `run` is a selection handle, not authority: it is resolved only among receipts whose recorded `leadThreadId` is the calling thread, then rechecked against the canonical receipt, occupied slot, checkout and app-server lease. Unknown or foreign ids fail before composing or recording a message. With both `run` and `requestId`, the two must resolve to the same receipt or the call fails before effects. With neither, one run is used implicitly; several runs return the bounded ambiguity list.

Evidence for the current suite: `cargo test -p codex-harness --test executor_mcp -- --test-threads=1` passed 35 tests, including active and idle steering, observed delivery, queue acceptance without evidence, native refusal and retry, two correlated questions on one run, identical questions bound to two different runs and leads, explicit lead run selection with mismatched/foreign refusals, repeated question text under distinct and omitted client ids, notification without a hold, duplicate and distinct payloads, lost acknowledgement, temporary lead absence, stale lease, sibling/foreign caller, forged arguments, above-one-mebibyte literal messages in both directions with no file relay, a large native record across interruption/reconnect, and no duplicate turn, phantom request or replay after MCP restart. The stop/continuation checks additionally cover exact-thread interruption, a sibling turn and terminal surviving, native terminal termination verified by exact inventory disappearance, repeated stop, completion/stop race, partial containment followed by verified cleanup, preserved commits and untracked files, unchanged slot/receipt/lease, refused post-stop delivery, exact same-thread continuation without assignment replay, fresh recovery that retains the predecessor, missing pre-turn history and refusal to continue an active thread. The preserved `executor_message` suite passed 67 tests, `executor_stop` passed 9, and `executor_control` passed 61 with two opt-in native checks ignored. These tests use the repository's real loopback control fixture, not a model-backed conversation.

A model-backed installed exchange with Codex 0.164.0 exercised both directions: an active lead received the question with `turn/steer`, an idle lead received the next question with `turn/start`, both questions appeared as native lead items without a status call or picker navigation, exact multilingual question and reply payloads matched their request ids, and the executor completed in one turn. A reply whose first result was `queued` was reconciled only after its native item became visible; a too-early retry remained `queued` and one later retry per request resolved it without creating a duplicate reply item or executor turn. Limits of this slice:

- There is no `executor_wait` adapter and no automatic final-result return. The lead can inspect the executor's native thread and current item history; actionable questions are returned by `executor_status`. Event-driven waiting and completion delivery remain task 3.3.
- MCP receipts written before the `lease` field existed are refused for status or messaging because their exact app-server binding cannot be proved. Receipts without the additive `prompt` and `control` records can still be stopped, but exact/fresh continuation refuses rather than fabricating an assignment or routing configuration. CLI dispatch, message and stop behavior is unchanged; new MCP dispatch records the lease, assignment, rendered prompt and exact thread configuration.
- The shared MCP transport now has one size owner: `mcp_protocol::MAX_FRAME` is 16 MiB (16,777,216 bytes) for one UTF-8 JSON frame, read in 64 KiB chunks. The former 16 KiB session argument check is removed rather than replaced by a second bound. An oversized frame fails explicitly with the exact limit and never reaches tool dispatch.
- The exchange and stop/continuation paths are verified by protocol fixtures and model-backed installed runs. Two-profile concurrency with differing feature settings, `/agents` UI behavior, elevated attachment and the installed UI proof remain tasks 1.2, 1.4 and 4.2.
- CLI dispatch, message, observation and stop remain compatible; no guidance cutover is part of this slice.

### Native MCP size, partial-read and reconnect boundary

The STDIO decoder owns the request bound. It buffers at most `MAX_FRAME + READ_CHUNK + 1` bytes for one unterminated frame, while the session admits at most two decoded envelopes ahead of the scheduler, one active operation and 64 queued requests. The request's 60-second deadline and the existing 64 KiB write chunk, 5-second response-write budget and bounded cleanup remain unchanged. Memory therefore stays bounded by those existing limits; no payload is written to a spill or relay, and the same bytes are not retained in a second durable record.

An MCP question or reply is composed as its header, the payload marker and the complete literal text. It does not pass through the CLI spill owner even above 256 KiB. The CLI compatibility routes still use that owner because their callers and tests remain; only the MCP transport stopped using it.

A partial frame is never dispatched: EOF before its terminating LF is an explicit `UnexpectedEof`, a malformed frame poisons the decoder, and an oversized frame reports that the frame exceeded 16,777,216 bytes. Each process connection starts a fresh decoder. There is no automatic reconnect, background retry or replay queue. A caller restart re-reads canonical receipts in sorted path order; the recorded run/thread/direction/client-message identity and content digest return an existing accepted attempt instead of sending it again. Read-only status/wait calls start no turn or assignment.

Checks on the reviewed tree exercise a 1,344,000-byte UTF-8 argument through the installed Codex 0.164.0 native MCP client without a model turn: the experimental app-server `mcpServer/tool/call` path connected to a test STDIO server, exposed its `echo` tool and returned the exact argument bytes. The native client's maximum is not claimed, only that it accepts more than one mebibyte. The same transport also passed a 1.3 MiB literal message in both directions, a native record above one mebibyte read, interrupted and re-read after MCP restart, partial and oversized frame failures with no tool dispatch, and a reconnect retry that produced no duplicate turn or phantom request. The focused `mcp_protocol` (6), `mcp_session` (4) and STDIO (12) checks passed; the 37 assignment tests and 67 CLI message compatibility tests also passed. The CLI spill tests remain as compatibility coverage and no working CLI relay path was removed.

### Executor MCP isolated-stop and continuation slice

`executor_stop` is bound by the same verified caller, canonical MCP receipt, occupied slot, exact checkout and app-server lease as status and messaging. A `run` argument selects only among the calling lead's verified receipts. The operation attaches to the recorded shared app-server, adopts the recorded executor thread, reads that thread's own active turn, and sends `turn/interrupt` with the exact thread and turn ids. It never reads the lead thread's active turn and never addresses the shared app-server process tree.

Child containment uses the native thread owner rather than an OS-tree guess. The installed Codex 0.164 protocol exposes `thread/backgroundTerminals/list` and `thread/backgroundTerminals/terminate`; the request processor loads the exact thread and parses the exact numeric `processId` before terminating that process. A model-free runtime probe against the installed 0.164 binary started an isolated app-server and thread, returned an empty exact-thread inventory, and accepted `thread/backgroundTerminals/terminate` with `{terminated:false}` for a nonexistent id. The MCP path records the exact thread's terminal inventory before and after interruption, terminates each listed process id, and polls the same inventory until the ids disappear or the bounded wait expires. A sibling thread's inventory is never read for termination, and a sibling turn and command remain running in the fixture.

Observed containment boundary: `ThreadBackgroundTerminal.osPid` is null on this route, so the evidence is the native owner's exact-thread inventory becoming empty, not an independently observed OS process identity. That is sufficient to report `containment: verified` for the native runtime's own command lifetime; it is not a claim that an arbitrary detached descendant was inspected. If the list or terminate method is unavailable, returns an error, leaves an id, or the turn remains active, the result is `partial` with the exact ids/thread state and the shared app-server is preserved. The same partial status blocks continuation until a repeated stop verifies containment.

The stop receipt records the native stop outcome, interrupted turn, observed thread state, containment counts and any surviving terminal or turn. Pending MCP deliveries and delivered-but-unresolved questions on that run become `cancelled`, are excluded from pending requests, and cannot restart the thread; message/reply delivery refuses until an explicit resume. The slot, owner, checkout, base, receipt path, assignment and lease are unchanged. Repeated stop re-reports or retries containment without a new interrupt, and a completion that wins the race is recorded as `already-completed` instead of stopped.

`executor_resume mode=exact` verifies the old thread has durable pre-turn history and no active turn, then submits one continuation turn on the same thread. The prompt names the preserved assignment objective and bounded caller progress, tells the model to inspect the diff, commits, untracked files and interrupted effects, and does not resubmit the assignment. A missing pre-turn history is an explicit error. `mode=fresh` starts one new thread on the same shared app-server with the preserved rendered assignment, records the predecessor thread/turn and stop record, and starts one assignment turn in the new thread. The predecessor remains retained and the pool is not reset, released or reassigned. Both modes record a bounded workspace fact (commits since the recorded base and changed/untracked path count) so interrupted effects are not assumed consumed.

The additive receipt fields are `assignment`, `prompt`, `control` (approval policy, sandbox, config overrides and role/profile argument identities), `stopTurnId`, `stopThreadState`, `continuation`, and for fresh recovery `predecessorThreadId` and `predecessor`. A continuation writes `continuedMs`/`continuedBy` into the stop record it follows; that marker is what permits later delivery, while a new stop record replaces it. Delivery refusal therefore survives a failure to write the follow-up cancellation list. Cache-loss thresholds, warning evidence and the CLI stop path are unchanged. Task 3.5 therefore remains open; this slice does not adapt cache-loss protection to exact-thread interruption.

### Executor MCP explicit release slice

`executor_release` is an explicit lead operation. The caller identity still comes only from `_meta.threadId`; a `run` argument selects among that lead's canonical MCP receipts but never establishes authority. The operation requires a `merged` or `discarded` disposition and a nonempty reason, resolves the repository's committed base unless `base` is supplied, and records one `release` object in the receipt. `executor_status` includes that record after the pool slot has left the occupied state. A release is not implied by native archive, status, wait, completion, stop or presentation.

The exact receipt, lead thread, run id, executor thread, slot, checkout and recorded app-server identity are revalidated before effects. The receipt's `lease.appServer` is the shared lead runtime identity, not a per-run host lease: its continuing liveness does not mean the executor run is active, and it is never used as evidence that release is safe. Run readiness is established from the exact executor thread instead: no active turn, no unresolved request, a loaded idle thread, no partial-stop containment and no startup reservation. A CLI session lease for the same owner is also refused through the existing liveness owner. Ambiguous, malformed, foreign or replaced receipts and slots fail before the pool owner is called.

The existing `task_worktree::release_slot` owner performs the reset. A clean run is reset to the selected committed base with `git reset --hard` and `git clean -fd`, which retains eligible ignored build caches; generated `.serena/` project state is tool state, so it is preserved and excluded from the cleanliness decision, while any other local or untracked work keeps the existing preserve/refuse behavior. `discarded` is the explicit authorization to delete local or untracked work. `merged` does not authorize deleting such work: if `git status --porcelain` is nonempty, the result is `preserved` with the checkout unchanged, the slot still occupied and its message payloads retained, and a later explicit `discarded` release may proceed. A reset limitation reported by the pool owner is likewise preserved with its concrete cause. On the release path, before the slot is freed, only the run's own receipt-recorded spilled message payloads are removed; another run's payload files are never scanned or deleted.

The receipt `release` record names the run, lead and executor threads, slot, checkout, disposition, reason, requested and actual base, reused or preserved outcome, slot state, limitation, message-removal result, repeat count and recording time. After the slot is free, repeating the same release with the same disposition returns that record with `idempotent: true` and no reset; changing the disposition is refused. A repeated release cannot address a later occupant: the canonical receipt and slot owner must still bind the original run. A preserved release can be retried after its cause is resolved, including changing `merged` to `discarded` to authorize deletion. The CLI `executor release` route and its compatibility tests continue to use the same pool owner and are not replaced by this adapter.

Deterministic release checks passed: `executor_mcp` 42/42 covers merged, discarded, repeated, active/pending, live-session lease, archive-only, foreign/ambiguous, stale/later-occupant, dirty-preservation, cache-retention and per-run payload cleanup cases; `executor_spawn` passed 43 with its one opt-in live test ignored, `executor_assignment` passed 37/37 and `worktree_pool` passed 14/14. `cargo check -p codex-harness --all-targets`, `cargo fmt --all -- --check`, strict OpenSpec validation, the installed source check (0 findings) and `git diff --check` also passed. This closes task 2.4; task 5.1 records the installed external-consumer acceptance below.

## Goals / Non-Goals

**Goals:** Keep native Codex responsible for model execution, conversation history, input delivery and presentation. Keep the harness responsible for its existing task/worktree lease, effective profile, caller-to-run relationship and acceptance lifecycle. Make the normal path intent-driven and preserve current behavior outside the changed executor surface.

**Non-Goals:** No Codex source changes, custom agent runtime, second mailbox/transcript store, plugin manager, replacement board, automatic merge, new provider route, or conversion of unrelated harness features. A messaging-only plugin would duplicate identity and lifecycle ownership and is not part of this change. Native child-agent registration is unnecessary.

## Decisions

### 1. One plugin with a thin Rust MCP entry point

Expose operations over shared existing executor services rather than invoking command strings or moving the whole CLI into MCP. Keep executable compatibility adapters using the same domain logic. The installed plugin bundles the MCP connection and concise owned skill guidance; native Codex owns plugin discovery/enabling, while the kit's current lifecycle owns delivered artifacts and recovery.

Start with these consumer operations; final exported names follow the installed plugin namespace without adding aliases:

| Operation | Necessary inputs and result |
| --- | --- |
| `executor_status` | Current caller scope; bounded owned runs, held slots, configured profile choices and availability, with native thread/detail references |
| `executor_dispatch` | Assignment, consuming repository when not already bound, committed base when needed, optional allowed profile; returns verified run/thread/slot/base and actual binding |
| `executor_message` | Literal content plus run or request reference when needed; request, notification or reply intent; returns correlated native delivery evidence |
| `executor_wait` | Owned run references and bounded wait; returns actionable question, terminal result, timeout or observation failure |
| `executor_stop` | Verified run reference; returns actual isolated stop outcome and preserved continuation identity |
| `executor_resume` | Saved run reference and explicit exact-continuation or fresh-recovery mode; returns preserved checkout and resulting thread binding |
| `executor_release` | Verified run reference, required `merged` or `discarded` disposition and nonempty reason, optional committed base; returns the actual reused or preserved pool outcome and receipt record |

Use native list/read/wait facilities for conversation inspection wherever they cover the need. The status/wait adapters add only existing pool/run and unresolved-request semantics absent from native thread state; they must not become another conversation store or polling scheduler. Do not publish separate tools for every internal helper or old command option.

MCP arguments carry literal structured data. Ordinary operations derive identity and installation state from verified bindings. Invalid mode combinations and ambiguous targets fail before effects; the lead never constructs endpoint URLs, temporary message files or full address tuples.

### 2. Attach to the native runtime that owns the lead

The preferred path connects the plugin to the native runtime already serving the originating CLI. If supported native startup does not expose the necessary connection, the only permitted adaptation is minimal bootstrap in the existing installed launcher: create a session-owned native app-server and attach the one native CLI client to it in the same terminal. Executors become threads in that runtime, with no additional conversation engine or per-executor UI processes.

A caller/thread binding must come from a supported native launch/call channel whose trust is demonstrated. User-supplied thread IDs, process titles, cwd, most-recent session selection and marker-only environments are insufficient. Validate both the originating lead and the executor's restricted return channel. Thread switching in /agents must not change an MCP caller's authority accidentally.

Use the CLI's privilege boundary. A standalone session-owned runtime is the candidate for elevated sessions because native elevated shared-daemon startup refuses by design. Supported authentication and attachment must also isolate integrity levels; same-account authentication alone is not assumed sufficient. Do not install a privileged service, silently lower privileges, expose an elevated endpoint to ordinary clients, or restart a live unrelated server.

**First-slice decision:** prove this attachment and authority path through a real installed plugin and native CLI. If the current extension points cannot provide it, preserve the working partial slice and exact failure and stop dependent migration. Neither separate executor terminals nor a file relay satisfies the agreed outcome. Any change of that outcome needs a new user decision; this plan grants no fallback architecture.

### 3. Profiles are resolved configuration, not model-name substitutions

Reuse the existing profile resolver and allowed executor bindings. Resolve native configuration with its source/precedence semantics, then apply only supported per-thread settings. Preserve provider authentication references, effort, features, instructions, MCP/tool availability and execution policies; do not copy credentials into tool results or repository artifacts. Keep the lead configuration unchanged and disable provider/model fallback.

Prove actual consumption, including the configured external executor profile and its differing feature settings, through a real request and native tool use. Metadata returned by thread/start is necessary but insufficient. A setting that is process-global and cannot differ as required is a preflight limitation, not permission to silently inherit the lead's value. Existing descendant-spawning restrictions must leave the executor's authenticated MCP reply channel usable.

The current local default profile remains a configuration choice, not a plugin constant. Acceptance follows the owner's currently allowed routes; it does not enable unconfigured providers for testing.

### 4. Native input and events own conversation exchange

Persist only the necessary originating-lead/run/thread/lease relationship and correlation references in the existing receipt/task lifecycle. Use native queue/turn/event identities for delivery reconciliation, native history for content and results, and existing board records for durable task decisions. Retire redundant relay/spill/transcript owners only after their accepted behavior is consumed through the new path.

For an active turn, use the supported addressed steering operation with the expected turn identity. For an idle conversation, enqueue supported native input and observe its actual start; queue acceptance can start a turn, so do not blindly also start one. Reconcile active-to-idle races and uncertain acknowledgements without resending text. Identical intentional messages remain separate operations.

The MCP call must not block waiting for its own recipient to answer. Native events drive request/action-required and completion delivery to the lead, including while it is waiting in a tool. A lead need not open /agents or ask for status to receive them. Verify this reentrant path for deadlocks and duplicates. Sending a correction does not kill the recipient's running command.

An unanswered request keeps the run nonterminal without model keepalives. Notifications do not create a reply hold. A reply resolves its exact request and resumes the same conversation; stopping or replacing a run invalidates delivery to that old identity, not to its successor. A temporarily absent lead remains the recorded recipient until supported explicit recovery changes ownership.

#### Bounded wait and result return

`executor_wait` is a caller-initiated observation, not a background scheduler or a model operation. It first refreshes the existing run receipt and returns an unresolved reply-required request without continuing to the timeout. Otherwise it reads the exact executor thread through `thread/read`, with the bounded paginated `thread/turns/list` fallback when an idle read omits history, at a 100 ms interval. Every native read bound fits inside the caller's remaining deadline, and the last interval returns a timeout rather than starting a read that cannot finish. The tool sends no `turn/start`, `turn/steer`, message or model request.

The receipt's accepted turn must still exist in that thread. The newest turn in the exact thread is the only one that can settle the observation, so an older completion cannot finish a continuation or a later message turn. A rejected, malformed or mismatched read remains an observation error. Failed, interrupted, present, empty and missing output are distinct outcomes, and a completion first observed after the caller's deadline is left for a later call.

The inline final message is bounded to 32 KiB and names truncation; exact thread and turn identities point back to native history and `executor_status` after UI navigation. The longest wait is 55 seconds because one MCP tool request has a 60-second transport deadline. The wait occupies only the calling MCP operation; executor questions and notices use their own tool connection in the exercised two-process path. Installed-runtime sharing of that connection remains part of the installed acceptance task. Result notices reuse the existing `executor_message` notification path and its recorded client identity; a retry reuses the receipt entry, and delivery means the item is present in the lead's native history, not that the lead read or applied it.

### 5. Shared runtime lifetime is separate from executor outcome

A native turn/result determines an executor outcome; app-server exit does not. Keep the existing distinction between completion, output defect, failure, stopped state and lead acceptance. Preserve the bounded result and native detail locator after UI navigation. Multiple user/tool turns in the same thread must not let an earlier completion finish newer work.

Stopping an executor uses exact-thread native interruption plus verified containment of its owned child work. A shared app-server process tree is never the target of run-local stop or cache-loss protection. If native containment cannot establish the promised isolated stop, that fails the first slice rather than weakening urgent-stop acceptance. Preserve current cache thresholds, evidence rules and native warning presentation; only its process-isolation assumption changes.

#### Exact-thread cache-loss slice

The MCP adapter reuses the existing `executor_cache` detector, `REQUIRED_MISSES`, support classification, evidence states and warning queue. The executor thread is the exact native session. The receipt's resolved `profile.modelProvider` and `profile.model` supply the same bounded identity the CLI receipts carry at top level; no provider name or counter field establishes support. A per-run background guard is deduplicated inside one MCP server process and is ensured on dispatch, status, wait, message/reply and explicit continuation. It reads only appended `token_usage_record` entries for that exact session, using the existing filesystem notification plus the one-second open-file reconciliation for delayed evidence. Historical usage may warm coverage but never counts as a new miss. A guard exits when the receipt's exact thread or turn changes, or when a stop has no continuation marker.

The installed 0.164 rollout shape was observed to carry `session_meta.payload.id` equal to the app-server thread id and `token_usage_record.thread_id` equal to it, with turn and usage counters. Discovery therefore uses the rollout's own metadata for the exact thread rather than a filename-only match or a second usage store.

At a qualifying loss the guard re-verifies the canonical receipt, occupied slot, run/thread/turn and exact app-server lease, then invokes the same exact-thread `mcp_stop` used by `executor_stop`. Native interruption records the actual stopped turn in `stopTurnId`; cache evidence binds that recorded turn, falling back to the accepted turn only when no native turn was stopped. It records the input, cached-input, miss, threshold, threshold-crossing count, resolved provider/model and bounded visible progress in `cacheGuard`. The stop records `stopped` or `partial-stop`, its containment detail and an `executor_resume` recovery: exact continuation reuses the same thread without assignment replay, while fresh recovery retains the predecessor. The shared app-server, its job, sibling turns, sibling terminals and the lead terminal are never addressed. A cache loss observed on historical usage or a cold/temporary sequence does not stop the run; a failed stop is recorded as `stopError` rather than as a successful stop.

Runtime limit: the installed app-server declares `warning` only as a server-to-client notification emitted by the app-server. The MCP process has no connection to the native lead frontend through which it could inject that notification, and the protocol has no client-to-server warning request. The MCP guard therefore records `diagnosticDelivery: "no-native-consumer"` and exposes its exact `warning` text and threshold evidence in the receipt, status and wait result. It does not write a terminal line, use a hidden relay or invent a second store. Native warning presentation remains verified only on the CLI frontend relay path; task 3.5 remains open for native MCP warning delivery even though exact-thread detection, stop and continuation are implemented.

Deterministic checks passed: `executor_mcp` 32/32, cache unit 17/17, `executor_warning` 26 passed with 2 opt-in ignored, `executor_stop` 9/9, self-reflection 10/10, and `executor_succession` 0 run with 2 opt-in ignored. `cargo check -p codex-harness --all-targets`, `cargo fmt --all --check`, strict OpenSpec validation and `git diff --check` also passed. The warning-delivery boundary above remains the only unimplemented acceptance item.

Exact continuation reconciles ownership and reconnects without resetting the pool. Fresh recovery creates a new bound thread from the preserved assignment and bounded progress, retains the predecessor, and checks interrupted effects. A failed pre-turn thread may have no durable rollout; keep the worktree and expose that fact. Normal release remains an explicit existing acceptance/discard operation, retaining ignored build caches.

### 6. Remove obsolete guidance at the working cutover

The active source owners include:

- `global/roles/lead.md` and affected executor role/context generation.
- `.agents/skills/team-lead/SKILL.md`, `.agents/skills/board-workflow/SKILL.md`, and `.agents/skills/token-efficient-workflow/references/session-reuse.md`.
- `docs/agent-delegation.md`, affected sections of `docs/rust-native.md`, `docs/project-decisions.md` and installation guidance.
- Generated briefs, tool descriptions, ordinary help, error and recovery hints, and lifecycle-delivered copies.

Remove migrated CLI mentions, fallback recipes and old-to-new tables from these required surfaces, rather than keeping both workflows in agent context. Do not author parallel machine-local skills. Protected external OpenSpec workflows and unrelated guidance stay untouched.

Existing command/package compatibility remains in code and targeted regression checks, not as active workflow advice. Retain only compatibility internals with actual callers; do not delete working paths solely because MCP no longer advertises them. Measure the existing byte/word and representative loaded-context acceptance with fixed assignments, including metadata and required references. The planning change does not switch installed instructions to tools that do not yet exist.

## Risks / Trade-offs

- **Native attachment or caller identity is unavailable:** the first real slice fails with a concrete API/identity boundary; retain partial work and stop broad migration.
- **Profile admission differs from actual execution:** verify provider/tool calls and effective settings, including features, before claiming profile support.
- **Elevated shared daemon refuses startup:** use a proven session-owned native attachment or report the unsupported boundary; ordinary daemon success does not prove administrator support.
- **Shared-process interruption affects neighbors:** test generation and a running child command beside a healthy executor; failure blocks replacement of the current control owner.
- **Native queues start turns or wake a busy lead differently than expected:** observe actual events and model-visible receipt; never infer delivery from a successful local write.
- **Plugin reconnection duplicates work or leaves questions unanswered:** reconcile exact native and lease identities, retain indeterminate states and test recovery without replay.
- **Context cutover leaves stale loaded instructions:** verify fresh installed lead and executor sessions as well as generated/source text; saved conversations may require supported fresh-context recovery.
- **Tests rely only on a toy fixture:** use fixtures for deterministic races/failures, then the existing real external-consumer acceptance with locally supplied private inputs. No quota exhaustion or newly enabled billing route is needed.

## Migration Plan

1. Deliver a minimal real MCP/native slice using existing pool and profile code. Prove two conversations in one CLI, distinct configured profiles/worktrees, a question/reply during active and idle states, automatic result return, isolated stop and continuation. Exercise ordinary and elevated attachment with actual command privilege.
2. After that proof, extract only shared executor logic needed by MCP and compatibility callers. Finish the changed contracts and targeted regression scenarios, including cache protection and preserved work.
3. Connect plugin packaging and registration to the existing install/update/check/recovery/disconnect lifecycle. Verify the installed artifact from a fresh external consumer without checkout-local imports.
4. Cut active guidance over to verified MCP names and remove obsolete context. Update the owning decisions with the new visibility and communication contract and retarget links; do not add historical migration manuals.
5. Complete integrated external-task acceptance, then record verified support and remaining version constraints in the existing guides. Only then retire proven-unused presentation/relay pieces.

A failed candidate leaves the currently installed working artifact and all task/worktree records intact. Lifecycle recovery restores the prior owned artifact without resetting work, reparenting active threads or overwriting unrelated settings. Recovery reports the actual available capability; it does not add a silent legacy dispatch recipe to new agent guidance.
